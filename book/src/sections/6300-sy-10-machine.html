Part AThe machine

Every performance question in this book has been answered in operations. That is the wrong currency. Arithmetic is nearly free and moving data is not, so the number that predicts how long a kernel takes is usually not the one anybody counted.

§1 The gap that organises everything

Arithmetic is cheap, memory is not

A modern accelerator performs of order 1014 floating-point operations a second and reads of order 1012 bytes a second from its memory. So it can do roughly a hundred operations in the time it takes to fetch one number.

That ratio is the subject of this movement. It means a computation that touches each value once is limited by the fetching, not the computing, and no amount of faster arithmetic helps it.

§2 The hierarchy

Go and read

Hennessy & Patterson, Computer Architecture: A Quantitative Approach. The reference for this movement. Read the memory-hierarchy chapter; everything else in this part's first half is a consequence of it.

Five levels, each roughly an order of magnitude apart

Registers: a few kilobytes, immediate. L1: tens of kilobytes, a few cycles. L2: hundreds of kilobytes to a few megabytes. Main memory: gigabytes, hundreds of cycles. Another machine's memory: over a network, microseconds.

Each level is roughly ten times larger and ten times slower. The whole craft of making numerical code fast is arranging that the data a computation needs is at the highest level it fits in, which is §12's subject and is why the same arithmetic can run at wildly different speeds.

§3 Arithmetic intensity

The number that predicts the answer

$$I = \frac{\text{floating-point operations}}{\text{bytes moved}}$$

Not the operation count and not the byte count, but their ratio. A kernel with low intensity spends its time waiting for memory; one with high intensity spends it computing.

Two examples fix the scale. Adding two vectors moves 24 bytes and does one operation: intensity 1/24. Multiplying two $n \times n$ matrices does $2n^3$ operations on $3n^2$ values: intensity proportional to $n$. Which is why matrix multiplication is the operation hardware is designed around and everything else is a problem.

§4 The roofline

Go and read

Williams, Waterman & Patterson (2009), Roofline: an insightful visual performance model. Where the model below comes from, and short. Its argument is that a single plot answers “what should I work on” better than a profile does, which is still true fifteen years later.

A ceiling with two pieces

Achievable throughput is bounded by $\min(I \times B, F)$: intensity times bandwidth, or peak arithmetic, whichever is smaller. Plotted against intensity on log axes it is a rising line meeting a flat one, and the corner is the ridge point.

Below the ridge you are memory-bound and the only remedies are moving less data or moving it from somewhere closer. Above it you are compute-bound and a better algorithm or lower precision is what helps. Knowing which side you are on decides what to work on, and it is a ten-minute measurement.

§5 Measured

One point that contradicts the rule of thumb

"Elementwise means memory-bound" is the usual summary and Figure 1 shows its exception: exp moves the same bytes as a copy and achieves 1.94 GB/s against the copy's 31 GB/s, because a transcendental function costs tens of operations per element. It is elementwise and compute-bound.

Which matters practically: fusing a chain of cheap elementwise operations helps a great deal and fusing a chain of activations helps much less, because the activations were not waiting for memory in the first place.

§6 Occupancy, and why it is not the goal

Pitfall: a metric that is a means

An accelerator hides memory latency by having many threads in flight: while one waits, another computes. Occupancy is how full that pipeline is, and it is the first thing every profiler reports.

It is a means to hiding latency, not an end. A kernel at 25% occupancy that keeps memory saturated is finished; raising its occupancy changes nothing. And raising occupancy usually means using fewer registers per thread, which can force values back to memory and make things worse. Optimise the time, and read occupancy only to explain it.

§7 Precision

Fewer bits buys two different things

Half the bits is half the bytes moved, which doubles the throughput of anything memory-bound, and it is separately faster in arithmetic, because the hardware has dedicated units for it. Those are independent gains and it is worth knowing which one you are getting.

What it costs is range and resolution, and the two failure modes differ. Overflow in a narrow format is catastrophic and loud; underflow in the gradients is silent, which is why loss scaling exists. Part XVII §19's mixed precision is this trade made carefully: compute in the narrow format, accumulate in a wide one.

§8 What movement A establishes

Three things

The currency is bytes moved, not operations. A hundred operations cost what one fetch costs, so the ratio decides.

The roofline tells you what to work on, and Figure 1 puts the ridge at 1.96 flops per byte on one machine (below it, only moving less data helps).

Elementwise does not always mean memory-bound. A transcendental moves the same bytes as a copy and runs sixteen times slower, so the rule of thumb has a large exception.
