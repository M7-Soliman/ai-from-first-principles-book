Part EConditional computation

§29 Not every parameter for every token

The idea

Everything so far applies every parameter to every input. Conditional computation breaks that: the model has many parameters and each input activates only a few, so capacity and cost per token stop being the same quantity.

The source book calls this dynamic structure and proposes it as an inference speedup: a cascade of classifiers, a gater choosing among experts. What it did not anticipate is that the same mechanism would be used to make training capacity cheap, which is the modern use.

§30 Mixture of experts

The construction

Replace a feed-forward block with $E$ copies, the experts, and a small router that scores them for each token. Each token is sent to its top $k$ experts, usually $k=1$ or 2, and the outputs are combined weighted by the router's scores.

The parameter count multiplies by roughly $E$; the compute per token multiplies by $k$. With $E=64$ and $k=2$ that is 64 times the parameters for twice the arithmetic, and it is why the headline parameter counts of large models decoupled from their cost.

The feed-forward is the block that gets replaced because it holds most of the parameters: Part XII's finding, and drill C1's 67%, arriving as a design decision.

Why the router has to be discrete, and what that breaks

Averaging all experts would defeat the point: the saving comes from not computing the ones you skip. So the routing is a hard top-$k$ selection, which is not differentiable.

The standard resolution is to weight each chosen expert's output by its router probability, so the gradient reaches the router through the magnitude of a selection that was itself discrete. It works, and it means the router is trained by a signal that never tells it about the experts it did not choose. That asymmetry is the source of §31's problem.

§31 Load balancing

Go and read

Fedus, Zoph & Shazeer (2022), Switch transformers. Top-1 routing, the auxiliary balancing loss and the capacity factor, all in §2.2. Worth reading for how directly it discusses dropped tokens, a number that is central here and is rarely reported by work that builds on it.

Why routers collapse without being told not to

Nothing in the loss rewards using all the experts. An expert that receives more tokens gets more gradient, improves faster, and is therefore chosen more often, a positive feedback loop that ends with a few experts doing everything and the rest untrained.

This is Part XIII §30's feedback loop, in the interior of a model: the router's choices shape the data each expert sees, which shapes how good each expert becomes, which shapes the router's choices.

The fix is an auxiliary loss that penalises imbalance: typically the product of the fraction of tokens routed to each expert and the mean router probability for it, summed over experts, which is minimised when both are uniform. It is added to the training loss with a small coefficient, and that coefficient is a real hyperparameter: too small and the router collapses, too large and it routes randomly, which discards the specialisation that was the point.

Pitfall: capacity factor, and tokens that are silently dropped

For the computation to be batched, each expert is given a fixed buffer: capacity factor $\times$ (tokens / experts). If more tokens route to an expert than fit, the overflow is dropped: passed through by the residual connection with no expert applied at all.

So a capacity factor of 1.0 with a slightly imbalanced router silently discards a fraction of the computation, and the loss curve shows a mild degradation with no indication of the cause. The number to log is the drop rate, and it is not on by default in most implementations.

Capacity factors above 1 buy safety with wasted memory and compute. The alternative (dropless routing, which sorts tokens by expert and uses variable-size grouped matrix multiplies) removes the problem at the cost of a much more complicated kernel, and is what current implementations do.

§32 What it actually buys, and what it costs

The honest accounting

Buys: more parameters at constant compute per token. Empirically a sparse model matches a dense one of similar total compute while having far more capacity, so at a fixed training budget it reaches a lower loss.

Costs, all of which are usually understated:

  • Memory does not shrink. Every expert must be resident somewhere. A model that is cheap per token still occupies its full parameter count, so it needs the same hardware to hold as a dense model of the same size.
  • An all-to-all per MoE layer. Tokens must be shipped to whichever device holds their expert, and the results shipped back. This is the most demanding communication pattern in this part, twice per MoE layer.
  • Load imbalance is a runtime tax, not only a quality issue: the step waits for the busiest expert.
  • Fine-tuning is harder, and sparse models are more prone to overfitting on small downstream sets, because the effective capacity per token is high and the data is not.

The summary that survives: MoE converts memory and interconnect into capacity. It is a good trade when you have the first two and want the third, and it is not a free improvement in any dimension.
