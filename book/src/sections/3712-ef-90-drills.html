PracticeDrills

Thirty-six problems. Most of this is arithmetic you can do before requesting any hardware, and two of them measure a technique failing to deliver what its FLOP count promises.

Tier 0 Estimate first

EstimateE1 · What decides your token rate

A 7-billion-parameter model in fp16, generating tokens one at a time. Write down the memory bandwidth needed to reach 30 tokens per second.

Answer. 420 GB/s: every weight is read once per token, so 14 GB × 30. Generation is memory-bound, not compute-bound, which is why quantization buys speed almost proportionally and why a faster matrix unit buys nothing at batch size one. Score yourself: within a factor of two is a pass, and an order of magnitude out is worth understanding before you go on.

Tier 1 Warm-up

WarmW1 · Two regimes

Name them and say why conflating them is an error.

Answer. Prefill processes the prompt in one parallel pass; decode generates one token at a time. Different bottlenecks, different optimisations, different costs. A 2,000-token prompt and a 200-token answer is one parallel pass and two hundred sequential ones.
WarmW2 · Arithmetic intensity

Define it, and give it for generating one token.

Answer. FLOPs per byte moved. Generating one token does two FLOPs per weight and reads every weight once, so it is 1, against a hardware ridge point of several hundred. The machine runs at a fraction of a per cent of its arithmetic capability.
WarmW3 · Why quantization helps

Decode is memory-bound. What follows for quantization and for pruning?

Answer. Quantization moves fewer bytes, which is the binding constraint, so it helps proportionally. Unstructured pruning removes arithmetic, which was not binding, so it helps not at all unless the format changes.
WarmW4 · The cache

Write the KV cache size and say what it is linear in.

Answer. $2 \cdot B \cdot T \cdot L \cdot H \cdot D \cdot$ bytes. Linear in both context and batch, which is why it, and not the weights, limits how many users fit.
WarmW5 · Outliers

Why do a few large weights hurt everyone?

Answer. The step size is set by the range, and the range is set by the largest value in the group. A handful of outliers inflate it, and every ordinary weight loses precision to accommodate them.
WarmW6 · What 2:4 buys

Why is 50% structured sparsity faster than 90% unstructured?

Answer. Because the pattern is regular enough for hardware to exploit: a two-bit position index per surviving weight, four bits of metadata per group of four, and a predictable access pattern. Unstructured zeros in a dense array cost exactly as much as any other number.
WarmW7 · Dark knowledge

What does a soft target carry that a label does not, and why raise the temperature?

Answer. The relative ordering over the wrong answers, a statement about the structure of the problem. A confident teacher's distribution is nearly one-hot, so raising $T$ is what makes that ordering numerically visible to the loss.
WarmW8 · Why LoRA costs nothing to serve

And what it gives up by merging.

Answer. $BA$ can be folded into $W_0$, giving an ordinary dense matrix. Merging gives up multi-tenancy: unmerged adapters let one base model serve many adaptations in a single batch, which is where the throughput comes from.
WarmW9 · Speculative decoding is exact

Why is it not an approximation?

Answer. The rejection rule (accept with probability $\min(1, p/q)$ and otherwise sample from the normalised positive part of $p - q$) makes the output distribution exactly the target model's.

Tier 2 Core

CoreC1 · The roofline

Implement arithmetic intensity and the roofline. Find the batch size at which a model of your choosing stops being memory-bound.

Answer. It is the ridge point, and it is usually in the hundreds. Below it, throughput is linear in batch size for free; above it, batching buys nothing more.
CoreC2 · Predict tokens per second

Estimate decode speed from model size, bytes per weight and memory bandwidth alone. Then compare to a real measurement if you have one.

Answer. Usually within a factor of two, with no benchmarking. The gap is the thing worth investigating: it is cache traffic, kernel overhead, or a batch you did not account for.
CoreC3 · When the cache overtakes the model

Compute the context length at which the KV cache equals the weights, for multi-head, grouped-query and multi-query attention.

Answer. Tens of thousands of tokens for multi-head, and the head-count factor moves it out proportionally. Then compute concurrent sequences on a real device size; that number is the one that decides serving cost.
CoreC4 · Quantization, three granularities

Implement per-tensor, per-channel and per-group symmetric quantization. Measure the error on a weight matrix with a heavy tail across bit widths.

Answer. Granularity buys more than an extra bit does, at the same storage. Then count the scales: at group 128 in 4 bits they add about 3%, which should be in any honest comparison.
CoreC5 · Find the outliers

Detect outlier channels, then quantize with the scales computed excluding them and the outliers kept exact. Compare to quantizing everything.

Answer. A large improvement, and note the trap: quantizing the whole matrix and then overwriting the outlier columns does almost nothing, because the scales were already inflated. The scales are the mechanism.
CoreC6 · Weight error is the wrong metric

Train a small model. Quantize it at several bit widths and plot both the weight error and the loss. Compare their shapes.

Answer. Weight error grows smoothly; loss stays flat and then falls off a cliff. Choosing a bit width from the first picks the wrong one.
CoreC7 · Sparse is bigger

Compute dense and CSR storage for a pruned matrix across sparsity levels. Find the crossover at which the sparse format finally becomes smaller.

Answer. Around two thirds sparsity, because each non-zero carries an index several times its own size. Below that, removing half the weights makes the file larger.
CoreC8 · Time it

Time a dense matrix multiply with 0%, 50%, 90% and 99% of the weights zeroed, then time a sparse-kernel version. Plot both against the speedup the FLOP count promises.

Answer. The dense line is flat at 1.0×, the whole point. The sparse kernel is slower until very high sparsity. Use the minimum of many runs rather than the mean; timing noise here is one-sided.
CoreC9 · 2:4

Implement it and confirm exactly half the weights survive and that they are the two largest in each group of four. Compare its accuracy cost to unstructured pruning at the same 50%.

Answer. Unstructured wins slightly on accuracy and loses entirely on speed. That trade, a constraint that makes the pattern predictable, is worth more than the freedom it costs.
CoreC10 · Prune and recover

Prune a trained model to 50%, 80% and 95%, fine-tuning after each. Plot accuracy against sparsity, with and without the fine-tuning step.

Answer. The fine-tuning is doing most of the work, and iterative pruning beats one-shot at the same final sparsity. Both are evidence about overparameterisation rather than about speed.
CoreC11 · Temperature and dark knowledge

Measure the entropy of a trained teacher's output at $T \in \{1, 2, 4, 8\}$, and check that the ordering of the wrong answers is preserved.

Answer. Near zero at $T=1$: the information is there and numerically invisible. Raising $T$ exposes it without changing the ranking, which is exactly what distillation needs.
CoreC12 · Distil, and the control

Distil a teacher into a small student. Then train the same student directly on the same data. Report both.

Answer. The gap is what the teacher was worth. This control is routinely omitted, and without it a distillation result says nothing about distillation.
CoreC13 · Distil with no labels

Repeat C12 using unlabelled data and the teacher's outputs alone.

Answer. It works, which is the practical claim: distillation needs unlabelled data rather than labelled, and unlabelled data is what you have.
CoreC14 · Self-distillation

Distil a model into an identical architecture and compare to the teacher.

Answer. Often better, with nothing compressed and no new data. Sit with how strange that is: the explanations are partial, and it is usually presented as though they were not.
CoreC15 · LoRA, implemented

Implement it, confirm the model starts exactly at $W_0$, and confirm the merged and unmerged forms compute the same function to machine precision.

Answer. The zero initialisation of $B$ is what gives the first property; the merge identity is what gives zero inference cost. Both are one line and both are worth checking rather than assuming.
CoreC16 · Is the update low rank

Fine-tune a model fully, take the SVD of each weight delta, and report the rank needed for 90% and for 99% of the energy. Compare to a random matrix of the same shape.

Answer. The spectrum decays sharply, and the 99% figure is several times the 90% one. Quote both: energy is not effect, and the 90% number alone overstates the case.
CoreC17 · Rank and placement

Sweep LoRA rank, and separately compare applying it to attention projections only against all linear layers at matched parameter count.

Answer. Placement usually matters more than rank. Matching the parameter count is what makes the comparison fair, and it is frequently not done.
CoreC18 · Batching, measured

Compute the throughput gain from batching under the roofline, and find where it stops being linear.

Answer. Linear up to the ridge, flat after it. Two orders of magnitude of utilisation live in that first stretch, which is why batching is not one optimisation among several.
CoreC19 · Paging

Given a realistic distribution of generation lengths, compute the cache wasted by reserving the maximum, and by paging into blocks.

Answer. The great majority against a few per cent. That recovered memory is concurrency, and concurrency is throughput.
CoreC20 · The cost model

Price a request end to end. Compare the cost of an input token to an output token, and check how each scales with batch size.

Answer. Output tokens cost far more, and the decode term is divided by the batch while the prefill term is not. That asymmetry is the shape of commercial pricing.

Tier 3 Stretch

StretchS1 · GPTQ, in miniature

Quantize a matrix column by column, adjusting the remaining columns after each to compensate for the error introduced. Compare to independent rounding at the same bit width.

Answer. Error compensation beats error minimisation, which is the insight: accept the rounding and fix its downstream effect rather than rounding better.
StretchS2 · Quantize the cache

Quantize keys and values to 8 and 4 bits separately and measure the effect on a long generation.

Answer. Keys are more sensitive, because they enter a softmax. And note that cache error accumulates over a generation where weight error is applied once, so a short-sequence measurement understates it.
StretchS3 · Speculative decoding, end to end

Train three drafts of increasing size. Measure the acceptance rate under the exact rejection rule and compute the implied speedup for each.

Answer. The best draft is small and close, and the product is what matters. Verify separately that the output distribution is unchanged: that is the property that makes the technique free rather than a trade.
StretchS4 · Serve many adapters

Hold one base model and several LoRA pairs. Serve a batch containing requests for different adapters and compare throughput to running separate merged models.

Answer. Far better, because the base multiply is shared across the whole batch. Then measure the per-sequence correction's cost: it is a low-intensity operation, so it is more expensive than its FLOP count suggests.
StretchS5 · Continuous batching

Simulate a queue with a realistic spread of generation lengths. Compare static and continuous batching on throughput and on p95 latency.

Answer. Several times the throughput at the same latency, from scheduling alone. Report percentiles, not means: the distribution is heavily skewed.
StretchS6 · Stack them

Apply 4-bit quantization, 2:4 sparsity and distillation to one model. Measure the size, the speed and the loss after each, in every order.

Answer. The compressions multiply and the accuracy costs add up faster than that. Order matters, and the combination is worth measuring rather than assuming from the individual results.
