Part FRunning a large job

§33 Batch size, and the critical batch size

Go and read

McCandlish et al. (2018), An empirical model of large-batch training. The gradient noise scale, and one of the few results in this part with a derivation rather than a fit. It predicts where parallelism stops buying wall-clock, and the prediction is checkable during a run you were going to do anyway.

Why bigger batches stop helping

A larger batch gives a less noisy gradient, so a larger step is safe and fewer steps are needed. That holds until the gradient is already accurate enough that removing more noise changes nothing: the critical batch size.

Below it, doubling the batch roughly halves the steps: the extra compute is free in wall-clock terms. Above it, doubling the batch costs twice the compute for almost no reduction in steps. Part IX §5's minibatch discussion, with the practical threshold named.

The useful estimator is the gradient noise scale: roughly the ratio of the gradient's variance to its squared norm, computable from two batch sizes during a real run. It rises as training proceeds, the gradient gets smaller and relatively noisier, so the critical batch size grows, which is the argument for batch-size schedules that ramp up.

Pitfall: the batch size chosen for the hardware, not the optimiser

§22 says data parallelism only stays efficient with enough tokens per device, so large runs want large batches. §33 says past the critical size those tokens are nearly wasted.

These pull in opposite directions and the resolution is not to pick one. It is to notice that a batch above the critical size is buying hardware utilisation with sample efficiency, and to say so, because reported as "we trained with a batch of four million tokens" it sounds like an optimisation decision when it was a networking one.

§34 Hyperparameter transfer

The problem, and μP

The best learning rate depends on model size, so a hyperparameter search at small scale does not transfer to large scale, and searching at large scale costs more than the run you are trying to configure. Part XIV §16's random search is unaffordable exactly where it is most needed.

Maximal update parameterisation fixes this by choosing how initialisation scales, how the learning rate scales, and how activations are multiplied, so that the optimal learning rate becomes independent of width. Tune on a small model, transfer the setting to a model a hundred times larger, and it remains near-optimal.

The scalings are not arbitrary; they follow from requiring that every layer's activations and updates stay the same order of magnitude as width grows, Part IX §16's initialisation argument, extended from the forward pass to the update.

Why this appears in a part about scale rather than about tuning

Without it, every large run is configured by extrapolating a guess, and the most common large-run failure is a learning rate that was fine at the size it was tested and is not at the size it was used.

It also affects the previous movement's measurements. A scaling study that uses one learning rate across model sizes systematically penalises the largest models, because that rate was right for one size. The correct protocol is to tune at every size, which is what this part's own scaling figure does, and it is the same class of error as §11's, in a smaller costume.

§35 Loss spikes and instability

What they look like and where they come from

Large runs show sudden jumps in the loss, sometimes recovering over hundreds of steps, sometimes not. They are more frequent at larger scale and are the single most common reason a large run has to be restarted.

The known contributors: attention logit growth, where the logits entering the softmax drift large enough to saturate it and produce vanishing gradients; numerical events in reduced precision, especially with fp16 and loss scaling; a learning rate that is fine on average and not for a particular batch; and unlucky data, a batch of repeated or degenerate text.

What is actually done about them
  • Gradient clipping, always. Part IX §9's cliffs, and the cheapest insurance in training.
  • Normalising the attention logits, by normalising queries and keys before the product, which removes the growth mechanism rather than reacting to it.
  • bf16 over fp16, which removes the loss-scaling failure mode entirely (§19).
  • Skip the batch. If a step's loss exceeds a running threshold, discard it. Crude, effective, and worth logging so the frequency is visible.
  • Rewind. Restart from a recent checkpoint with a different data order. Sometimes the spike is a specific batch, and it will not recur.

§36 What to log

The panel for a long run

Part XIV §12's instruments, plus the ones specific to scale:

  • Loss, and validation loss on a held-out set that is genuinely held out.
  • Gradient norm, before clipping, and the fraction of steps clipped.
  • Update-to-parameter ratio per layer (Part XIV §12), which is the one that transfers across scales.
  • Tokens per second, and utilisation as a fraction of the hardware's peak. If this drifts down, something is degrading.
  • Loss-scale value if using fp16, and every overflow event.
  • Expert load and drop rate if using MoE (§31), which are off by default.
  • Time since the last checkpoint, and the restart count.

The discipline that matters: decide these before the run starts. A month-long job that was not instrumented cannot be diagnosed afterwards, and re-running it to add a metric is not an option.

§37 The cost model

Estimating a run before requesting it

Two approximations carry most of the arithmetic. Training a dense transformer costs about $6N$ FLOPs per token: two for the forward pass's multiply-accumulate, four for the backward, which is roughly twice the forward. Inference costs about $2N$ per token.

So a run's total compute is $C \approx 6ND$, and its wall-clock is that divided by the hardware's sustained throughput, which is not its peak. A realistic sustained fraction is 30–50% for a well-tuned large run, and the difference between assuming 100% and measuring 40% is a factor of two-and-a-half in the schedule and the budget.

That gap is not slack to apologise for; it is bounded by the same arithmetic everywhere it shows up. An unfused sequence of small operations round-trips its inputs and outputs through memory between each one, and the step's realised throughput is capped by whichever of arithmetic or memory bandwidth is scarcer for the kernels actually launched, not for the ones a whiteboard FLOP count assumes. Kernel fusion and compilation close part of that gap by turning several memory-bound operations into one more arithmetic-bound one. Part XIX §3 develops the full argument (arithmetic intensity and the roofline model) for the inference side of the same hardware; it is the same ceiling that sets the 30–50% here.

Do this arithmetic first. It takes ten minutes, it decides whether the plan is feasible, and §14's allocation question cannot be answered without it.

§38 When scale is the wrong answer

Five cases, and they are common

The data is the constraint. If you have exhausted the available data, more parameters move you along the wrong axis. §13's frontier says so quantitatively.

The task is mis-specified. Part XIII §6: the labels define the task, and a larger model fits a wrong specification better. Part XIV §35's four possibilities apply unchanged.

The metric has saturated. If the benchmark's remaining headroom is label noise (Part XIV §22), a larger model buys a number and not a capability.

The bottleneck is elsewhere. Retrieval, tool use, a better prompt or more inference-time compute frequently beat a larger model at a fraction of the cost, and the comparison is rarely made because it is nobody's project.

The validity question is untouched. Part XIII §21 and Part XV §40 both established this: scale improves precision and does nothing for validity. If the corpus underrepresents a population or the augmentation discarded the signal, a bigger model does the same thing more confidently.

§39 What to carry forward

The one thing

Scale is arithmetic before it is anything else.

Almost every decision in this part was settled by counting rather than by experiment. Memory is $16N$ bytes plus activations you can compute. The pipeline bubble is $(P-1)/(M+P-1)$. The all-reduce moves $2N$ values per step regardless of batch. Training costs $6N$ FLOPs per token. Compute-optimal allocation follows from a fitted surface and a constraint.

None of that needs hardware to work out, and all of it decides whether a run is possible. The teams that are good at this do the arithmetic first and are rarely surprised; the failure mode is starting the job and discovering the constraints one out-of-memory error at a time.

The second thing, because it recurs: the empirical laws are fits, and a fit inherits every choice made in the runs it was fitted to. The most consequential scaling result of the decade was wrong for four years because of a learning-rate schedule. Ask what was held fixed.
