Part AThe operation

§1 Why a dense layer is the wrong shape for an image

In 60 seconds

A dense layer connects every input to every output. On an image, that is not merely expensive. It is absurd: one layer on a modest photograph would need more parameters than every weight in an eight-billion-parameter language model. And the extravagance buys nothing, because it spends its capacity learning separately, at every position, a fact that is true everywhere.

Every network so far has been built from the layer of Part VII §5: multiply by a matrix, add a bias, apply a nonlinearity. That layer makes exactly one structural assumption, which is that it makes none. Every input may affect every output, and the model is left to discover from data which connections matter.

For a 784-dimensional vector of handwritten-digit pixels, that is affordable. For a photograph it is not, and the arithmetic is worth doing rather than gesturing at.

The fourth power is the part to hold on to. Doubling the resolution of your images multiplies the dense layer by sixteen. There is no hardware trend that outruns that, and there never was.

Why the cost is the smaller objection

Suppose the parameters were free. The dense layer would still be the wrong model, for a reason that has nothing to do with memory.

An edge detector that works in the top-left corner of an image works in the bottom-right corner too. The physics does not change across the frame. But a dense layer has a separate parameter for every (input pixel, output pixel) pair, so it must learn the edge detector independently at every position, and it must see edges at every position in the training data to do it.

That is Part VI §6's capacity argument arriving from an unfamiliar direction. The dense layer's capacity is not too small; it is spent on the wrong thing. It is using millions of parameters to express a fact that could be written down once, and it needs the data to pay for every copy.

So the goal of this part is to build a layer that assumes something (specifically, that a useful pattern is the same pattern wherever it appears) and to be precise about what that assumption costs when it is wrong. Part VIII §3 said a regulariser is a preference expressed before you know which functions fit. An architecture is the same thing, stated more forcefully, and §11 will make that identification exact.

§2 Convolution

Go and read

LeCun et al. (1998), Gradient-based learning applied to document recognition. The convolutional network, complete, from the group that built it, and worth reading for what it is not. There is no new mathematics here and no clever trick; there is a clearly stated architecture and a system that went on to read a tenth of the cheques in the United States. Read §II for the design and the rest for a reminder that this was engineering long before it was research.

The operation predates its use here by a long way, and the cleanest way in is the one that motivated it.

Suppose you are tracking something with a noisy sensor that reports a position $x(t)$ at every instant. Any single reading is unreliable, so you would rather report an average of several. But not a plain average: recent readings are more relevant, so you want a weighted average, with the weight depending on how old a measurement is. Write that weighting as $w(a)$, where $a$ is the age. Applying it at every moment gives a smoothed estimate

$$s(t) = \int x(a)\,w(t-a)\,da$$

and that operation is convolution, written $s = x * w$.

Discrete convolution, one and two dimensions

Computers sample time, so the integral becomes a sum:

$$s(t) = (x*w)(t) = \sum_{a=-\infty}^{\infty} x(a)\,w(t-a)$$

and with a two-dimensional image $I$ and a two-dimensional kernel $K$:

$$S(i,j) = (I*K)(i,j) = \sum_m \sum_n I(m,n)\,K(i-m,\,j-n)$$

The first argument is the input, the second the kernel, and the result the feature map. The sums are infinite in principle and finite in practice, because everything is zero outside the region you actually stored.

Two things about that definition deserve attention before anything is built on it.

The kernel is not a smoother here. In the sensor example $w$ had to be a probability density, or the result would not be an average at all. In a network the kernel is a set of learned parameters with no such constraint: it will happily be negative, and the useful ones usually are, because subtraction is how you detect a change. The operation is inherited; the interpretation is not.

The index runs backwards. In $K(i-m, j-n)$, as $m$ increases the index into the input increases and the index into the kernel decreases. The kernel is flipped. That is a real feature of the definition and it is about to be discarded.

§3 Cross-correlation, and why everyone calls it convolution

Flipping the kernel buys exactly one property: commutativity, $I*K = K*I$. It is useful when writing proofs and irrelevant when writing networks, so essentially every library implements the unflipped version

$$S(i,j) = \sum_m \sum_n I(i+m,\,j+n)\,K(m,n)$$

which is properly called cross-correlation, and calls it convolution anyway. This book follows that convention and flags the difference where it matters.

Why the sloppiness is harmless here, and where it is not

The kernel is learned. An algorithm that flips will learn a kernel that is the mirror image of what an algorithm that does not flip would learn, and the two networks compute the same function. Nothing observable depends on the choice.

Nor is commutativity missed. Convolution is never used alone: it is composed with a nonlinearity and other layers, and that composition does not commute regardless.

It does matter in two places. When you load weights trained in another framework that made the other choice, a silently mirrored kernel is a real bug and a confusing one. And when you are checking an implementation against a signal-processing reference, which will flip, because in that field commutativity is load-bearing.

The general lesson is Part IV's: a name in a library is a historical artefact, not a definition, and conv2d is the clearest example in the whole toolkit.

§4 Convolution is a matrix multiplication

In 60 seconds

Convolution is linear, so by Part I §4 it is multiplication by some matrix. That matrix exists, it is enormous and almost entirely zero, and every one of its nonzero entries is a copy of one of the handful of numbers in the kernel. Seeing it explicitly is the shortest route to everything in this part: the parameter count, the backward pass, and what "parameter sharing" actually constrains.

Nothing in §2's definition is nonlinear: the output is a sum of input values times fixed coefficients. So flatten the image into a vector and there must be a matrix $M$ with $\mathbf{s} = M\mathbf{x}$. Building it is a two-line exercise: for each output position, lay the kernel into a blank image at that offset and flatten the result into a row.

Toeplitz, and doubly block circulant

A matrix in which each row is the row above shifted by one is Toeplitz. That is the structure of $M$ for one-dimensional convolution, and it is exactly what "the same operation at every position" means when written as a matrix.

In two dimensions the shift happens at two scales (within a row of the image, and from one row to the next) and the resulting structure is called doubly block circulant. Figure 2's stripes are it. The deviation of each row from a pure shift of its predecessor was measured at exactly zero.

Intuition: two constraints, and they do different jobs

$M$ is constrained in two independent ways, and it is worth separating them because §7 and §8 will price them separately.

It is sparse. Most entries are zero, because the kernel is much smaller than the image and an output pixel simply does not see most of the input. This is sparse interaction, and on its own it would still leave you with 324 free parameters here.

Its nonzero entries repeat. Only 9 distinct values appear among the 324. This is parameter sharing, and it is what takes the count from 324 to 9.

You can have either without the other. A locally connected layer (§8) is sparse without sharing. A recurrent network shares without being sparse. Convolution is both, and most of its properties trace to one or the other rather than to the pair.

One consequence is immediate and will be used in §16. Because convolution is a matrix multiplication, any algorithm that works with matrix multiplication works with convolution, including backpropagation, which needs only $M^\top$. Real implementations specialise heavily for speed, but nothing in the theory requires it.

§5 Padding, stride, and the arithmetic of size

Applied literally, convolution shrinks its input. A kernel of width $k$ has $k-1$ fewer valid positions than the image has pixels, so an image of width $m$ gives an output of width $m-k+1$. Stack layers and the shrinkage compounds until nothing is left: with a width-6 kernel on a 16-pixel input you get three layers, and the last one cannot move.

The fix is to pad the input with implicit zeros. Three settings have names.

Valid, same, and full
PaddingOutput widthProperty
valid: none$m-k+1$ Every output pixel sees the same number of inputs. The representation shrinks, which bounds the depth.
same: $k-1$ zeros$m$ Depth is unbounded. But border pixels influence fewer outputs than central ones, so they are under-represented.
full: $2(k-1)$ zeros$m+k-1$ Every input pixel is visited $k$ times in each direction. Now the output pixels near the border see fewer real inputs.

The best setting for test accuracy is usually somewhere between valid and same, and same is the near-universal default because unbounded depth is worth more than the border effect costs.

Stride is the second control. Rather than evaluating the kernel at every position, evaluate it every $s$ positions:

$$Z_{i,j,k} = \sum_{l,m,n} V_{l,\,(j-1)s+m,\,(k-1)s+n}\; K_{i,l,m,n}$$

which is mathematically identical to convolving with stride one and then throwing away all but every $s$-th output; this is computationally quite different, because the two-step version computes a large number of values in order to discard them.

The size formula, and the one number people get wrong

For input width $m$, kernel $k$, padding $p$ on each side, stride $s$ and dilation $d$ (§29):

$$\text{output width} = \left\lfloor \frac{m + 2p - d(k-1) - 1}{s} \right\rfloor + 1$$

Set $d=1$, $s=1$, $p=0$ and it collapses to $m-k+1$. Set $p=(k-1)/2$ with odd $k$ and it gives $m$, which is why kernels are almost always odd-sized. An even kernel cannot be padded symmetrically, so same padding has to put one more zero on one side than the other, and your feature maps quietly drift half a pixel per layer.

The floor is where the errors live. With $s>1$ the last few columns can be dropped entirely if they do not fill a whole stride, and no framework will warn you.

§6 Channels, and the shape bookkeeping

Two departures from §2 remain, and both are about the fact that real inputs are not a single grid of numbers.

Many kernels at once. One kernel extracts one kind of feature at many positions. You want many kinds, so a layer holds a stack of kernels and produces one feature map each.

Many channels in. A colour image has three values per pixel. The output of one convolutional layer has as many values per position as it had kernels. So the input is a grid of vectors, and a kernel must span all of them.

Multi-channel convolution

With a 4-D kernel tensor $K$, where $K_{i,l,m,n}$ is the weight from input channel $l$ to output channel $i$ at offset $(m,n)$:

$$Z_{i,j,k} = \sum_{l,m,n} V_{l,\,j+m-1,\,k+n-1}\;K_{i,l,m,n}$$

Summed over input channels $l$ and over the spatial offsets $m,n$. The sum over $l$ is the important one: each output channel is a function of every input channel, so a convolutional layer is local in space and fully connected across channels.

Shapes, once, properly

$$\underbrace{(N, C_{\text{in}}, H, W)}_{\text{input}} \;*\; \underbrace{(C_{\text{out}}, C_{\text{in}}, k, k)}_{\text{kernel}} \;\longrightarrow\; \underbrace{(N, C_{\text{out}}, H', W')}_{\text{output}}$$

Parameters: $C_{\text{out}} \times C_{\text{in}} \times k^2$, plus $C_{\text{out}}$ biases, one bias per output channel, shared across every position, which is the natural choice when the kernel is shared across every position too. It is not the only choice ch09 §9.5 records: a fixed-size input can instead take one bias per output position, and the locally connected and tiled layers of §8 pair naturally with a per-unit or per-tile bias, matching whatever sharing their weights use. This part builds only the shared, per-channel case, which is what every architecture in it actually ships.

Multiply-accumulates: $N \times C_{\text{out}} \times C_{\text{in}} \times k^2 \times H' \times W'$. Note which factors are in the parameter count and which are not: the spatial size $H'W'$ costs compute and no parameters. That asymmetry is why a convolutional network can be small and slow at the same time, and it catches people who budget by parameter count.

Pitfall: channels-first and channels-last

PyTorch stores images as $(N, C, H, W)$; TensorFlow, most image libraries, and every file format you will load from store them as $(N, H, W, C)$.

Both are defensible (channels-last has better memory locality for some kernels, which is why PyTorch also offers it as a memory format) and the conversion is one permute. The failure mode is that a $(32, 32, 3)$ array fed to a layer expecting channels-first is interpreted as 32 channels of a $32\times3$ image, which is a perfectly valid tensor of the wrong thing. It does not raise. It trains. It produces a model that is merely bad, and Part IV §17's debugging order exists for exactly this.

Try it

A layer takes $(N, 64, 56, 56)$ and applies 128 kernels of size $3\times3$ with stride 1 and same padding. Give the output shape, the parameter count and the multiply-accumulate count per image. Then say which of the three changes if you halve the image size.

Answer. Output $(N, 128, 56, 56)$: same padding preserves the spatial size and the channel count is set by the number of kernels.

Parameters: $128 \times 64 \times 3 \times 3 = 73{,}728$, plus 128 biases: 73,856.

Multiply-accumulates: $128 \times 64 \times 9 \times 56 \times 56 = 2.31\times10^{8}$ per image.

Halving the image to $28\times28$ leaves the parameter count completely unchanged and divides the compute by four. That is the asymmetry above, and it is the reason a convolutional layer's cost cannot be read off its size: the same 73,856 parameters cost $2.3\times10^{8}$ operations at $56\times56$ and $1.5\times10^{10}$ at a full $448\times448$.
