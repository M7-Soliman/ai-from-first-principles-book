Part DBackward, and fast

§16 The backward pass of a convolution is a convolution

In 60 seconds

§4 said convolution is multiplication by a matrix $M$. Part VII §14 said backpropagation through a linear map is multiplication by its transpose. Put those together and the backward pass needs $M^\top$, which turns out to be another convolution, with the kernel flipped and the padding changed. Verified here to exactly zero.

A convolutional layer needs three operations, not one, and it is worth naming them separately because they have different shapes and frameworks expose all three.

The three operations

Write $Z = c(K, V, s)$ for the strided convolution of §5, and suppose backpropagation has delivered $G_{i,j,k} = \partial J / \partial Z_{i,j,k}$.

1. Forward. $c(K, V, s)$ itself.

2. Gradient with respect to the kernel, needed to learn:

$$g(G, V, s)_{i,j,k,l} = \frac{\partial J}{\partial K_{i,j,k,l}} = \sum_{m,n} G_{i,m,n}\,V_{j,\,(m-1)s+k,\,(n-1)s+l}$$

Note: $k$ and $l$ here are kernel spatial offsets, not the output indices they name in $G_{i,j,k}$ above. This reuse follows Goodfellow et al. eqs 9.11–9.13; the matrix view below is cleaner.

3. Gradient with respect to the input, needed to go deeper:

$$h(K, G, s)_{i,j,k} = \frac{\partial J}{\partial V_{i,j,k}} = \sum_{\substack{l,m \\ (l-1)s+m=j}}\;\sum_{\substack{n,p \\ (n-1)s+p=k}}\;\sum_q K_{q,i,m,p}\,G_{q,l,n}$$

These three suffice to train a convolutional network of any depth.

The formulas are unenlightening. The matrix view is not.

Worked: the input gradient, derived and then recognised

Flatten everything. Forward is $\mathbf{z} = M\mathbf{x}$, and Part VII §14's rule gives the input gradient as

$$\frac{\partial J}{\partial \mathbf{x}} = M^\top \frac{\partial J}{\partial \mathbf{z}}$$

Now look at what $M^\top$ is. In $M$, row $p$ holds the kernel positioned at output location $p$. Transposing turns those rows into columns, so column $p$ of $M^\top$ holds the kernel at location $p$; row $q$ of $M^\top$ collects, for input pixel $q$, every kernel weight that ever touched it.

An input pixel is touched by the kernel at every output position that reaches it, and it is touched by a different kernel element at each. Reading those off in order gives the kernel reversed. And the pixels at the border are reached by fewer output positions, which is the signature of full padding rather than valid.

So $M^\top$ is a convolution with the flipped kernel and full padding. Measured on a $3\times3$ kernel over an $8\times8$ image, the difference between $M^\top\mathbf{g}$ and that convolution is exactly $0.00$, not approximately, in float64.

Why this is worth more than a derivation

Three things follow, and only the first is about backpropagation.

You need no new machinery. A library that can convolve can differentiate through convolution, using the operation it already has. This is why convolutional networks were trainable in 1989 with the software of 1989.

The transpose is a useful operation in its own right. Anything that must go from a low-resolution representation back to a high-resolution one (segmentation decoders, autoencoders, generative models) needs $M^\top$, and §27 meets it again under the name transposed convolution. It is the same operation, used forwards.

Care is needed about output size. Several input sizes can produce the same output size once striding and padding are involved, so the transpose cannot infer what to produce and must be told. That is the origin of output_padding, which otherwise looks like an arbitrary parameter.

§17 How it is actually computed

Nobody builds $M$. It is $O(HW \cdot HW)$ entries to express $O(k^2)$ numbers, which is the opposite of a good idea. But the observation that convolution is a matrix multiplication is still how it gets computed fast: you just build a different matrix.

im2col

Rather than expanding the kernel into a huge sparse matrix, expand the input into a dense one. For every output position, gather the patch the kernel will see and write it as a column. That gives a matrix of shape $(C_{\text{in}}k^2) \times (H'W')$.

Reshape the kernel stack to $C_{\text{out}} \times (C_{\text{in}}k^2)$ and the entire convolution is one matrix multiplication.

The point is not that multiplication is cheaper in operation count: it is the same arithmetic. It is that a large dense matrix multiplication is the single most optimised routine in computing, and reshaping your problem into one inherits fifty years of that work.

Pitfall: this is where your memory went

Part VII §17 established that training memory is dominated by stored activations rather than parameters. im2col sharpens that: the transient patch matrix is $k^2$ times the input, so a $3\times3$ layer briefly needs nine times its input in scratch space, and a $5\times5$ layer twenty-five.

This is why an out-of-memory error can arrive on the forward pass of a layer whose parameters are tiny, and why reducing batch size fixes it while reducing model size does not. Modern kernels avoid the full materialisation (they tile the computation so only a block of the patch matrix exists at once) but the naive version is still what most educational implementations do, including the one you will write in this part's project.

§18 Separable kernels, and the other algorithms

Three further routes to a faster convolution, each exploiting a different structure.

Separable kernels. If a $d$-dimensional kernel is the outer product of $d$ vectors, convolving with it is the same as applying $d$ one-dimensional convolutions in turn. That takes the cost from $O(w^d)$ to $O(w \times d)$ in both time and storage. A Gaussian blur is separable; so is a box filter. Most learned kernels are not, which limits this to fixed filters, but it is the origin of the idea §19 generalises.

The Fourier transform. Convolution in space is multiplication in frequency, so you can transform both operands, multiply pointwise and transform back. For large kernels this wins; for the $3\times3$ kernels that dominate modern networks the transform overhead dominates, and it is rarely used.

Winograd. A minimal-filtering algorithm that computes small convolutions with fewer multiplications than the direct method, at the cost of more additions and some numerical precision. It is what actually runs when you convolve $3\times3$ kernels on modern hardware, and it is a good example of an old algorithm (1980, for a different purpose) becoming load-bearing infrastructure.

Why inference-only speedups are worth as much as training ones

It is tempting to dismiss an optimisation that helps only the forward pass. In practice the forward pass is where nearly all of the lifetime compute goes.

A model is trained once and served indefinitely. A network trained for a week and deployed for two years spends the overwhelming majority of its total compute on inference, so a 20% forward-pass improvement is worth far more than a 20% training improvement; that is why quantisation, distillation and pruning are all inference-side techniques that nonetheless get research attention.

§19 Depthwise separable convolution

In 60 seconds

§6 noted that a convolutional layer is local in space and fully connected across channels. That second half is a dense layer hiding inside your convolution, and it holds most of the parameters. Split the operation in two (mix space, then mix channels) and the cost falls by a factor of about nine, with a formula that is exact.

ch09 mentions, almost in passing, that you can restrict each output channel to depend on only a subset of the input channels: connect the first group of outputs to the first group of inputs, and so on. That is grouped convolution. It appeared in AlexNet for a mundane reason (the model did not fit on one GPU) and was later recognised as a design axis in its own right.

Push it to the limit. Let every group be a single channel. The architecture that made this the default construction for efficient inference is MobileNet (Howard et al., 2017), which built entire networks from depthwise separable blocks and demonstrated that the ninefold parameter saving translates to deployable models on phones and embedded devices, though, as the pitfall below explains, parameter saving and wall-clock saving are different things.

Depthwise separable convolution

Replace one $k \times k$ convolution from $C_{\text{in}}$ to $C_{\text{out}}$ channels with two operations:

  1. Depthwise: a $k \times k$ convolution applied to each input channel independently. Mixes space, not channels. $C_{\text{in}}k^2$ parameters.
  2. Pointwise: a $1 \times 1$ convolution. Mixes channels, not space. $C_{\text{in}}C_{\text{out}}$ parameters.

The ratio to a standard convolution is

$$\frac{C_{\text{in}}k^2 + C_{\text{in}}C_{\text{out}}}{C_{\text{out}}C_{\text{in}}k^2} = \frac{1}{C_{\text{out}}} + \frac{1}{k^2}$$

Intuition: the $1\times1$ convolution is not a convolution

A $1\times1$ kernel has a receptive field of one pixel. It cannot detect an edge, a corner, or anything spatial whatever. So what is it doing?

It is a dense layer applied independently at every position, mapping the vector of $C_{\text{in}}$ channel values at each pixel to a vector of $C_{\text{out}}$ values, with the same matrix everywhere. Read that way, the name is misleading and the operation is obvious: it is a learned recombination of features, position by position.

Which is why it appears everywhere once you look. It is how Inception reduces channel count before an expensive layer; how ResNet's bottleneck blocks squeeze and expand; how a segmentation head turns features into per-pixel class scores; and how the pointwise half of a separable convolution does its job. A $1\times1$ convolution is the channel-mixing operation, and separating it from spatial mixing is what §19 is really about.

Pitfall: nine times fewer parameters is not nine times faster

The parameter saving is exact. The wall-clock saving is usually much smaller, and sometimes negative.

Depthwise convolution does very little arithmetic per byte of memory it touches; it is memory-bound, where a standard convolution is compute-bound. Modern accelerators are built for arithmetic intensity, so an operation that reduces arithmetic without reducing memory traffic can leave the hardware idle. Reported speedups of $9\times$ in FLOPs routinely deliver $2$–$3\times$ in latency.

This is the general lesson from Part IV, in a new setting: FLOPs are not time, and a paper reporting only FLOPs is reporting the number that flattered it. Measure latency on the hardware you will deploy on.

In the framework: one function, and its arguments are this whole part

Having derived the operation, the mapping is direct. Every structural choice in §§5, 6, 8 and 19 is an argument to the same call.

import torch.nn as nn

# the standard layer of section 6
nn.Conv2d(64, 128, kernel_size=3, stride=1, padding=1)

# section 5: 'same' padding, computed for you (odd kernels only)
nn.Conv2d(64, 128, 3, padding="same")

# section 19: depthwise, then pointwise
nn.Sequential(
    nn.Conv2d(64, 64, 3, padding=1, groups=64),   # groups == in_channels
    nn.Conv2d(64, 128, 1),                        # the 1x1 channel mixer
)

# section 16, used forwards
nn.ConvTranspose2d(128, 64, 4, stride=2, padding=1)

What each piece corresponds to. groups=g is §19's restricted channel connectivity: the input and output channels are split into $g$ groups and each output group sees only its own input group. groups=1 is the ordinary layer; groups=in_channels is depthwise. The parameter count divides by $g$ exactly, which you can check against Figure 7.

Why it is designed that way. There is no separate depthwise operation because there does not need to be; grouping is the general mechanism and depthwise is its extreme. That is a good API: one axis, with the special cases at its ends.

What breaks. Three things.

padding="same" raises on a strided convolution: padding='same' is not supported for strided convolutions. §5's arithmetic says why: with $s>1$ there is generally no padding that preserves the size, so rather than pick something silently PyTorch refuses. With an even kernel it does not refuse; it pads asymmetrically, preserves the size, and emits a warning that it may need to copy the input. That asymmetry is invisible and it accumulates, which is the argument for odd kernels made in §5.

groups must divide both channel counts, and the error names only the first: in_channels must be divisible by groups. If your output count is the offending one you will be looking in the wrong place.

ConvTranspose2d cannot infer its output size: §16's warning, and it is easy to see why. With $k=3$, $s=2$, $p=1$ a forward convolution maps both an input of 7 and an input of 8 to an output of 4. Going backwards from 4, both answers are correct, so the transpose returns the smaller and output_padding=1 asks for the larger. Note also that kernel_size has no default here: §27's divisibility condition makes the choice consequential enough that the library declines to guess.
