§8 nn.Module, and what parameters() is

In 60 seconds

A Module is an object that owns tensors and knows which of them are being learned. That second half is the whole point: model.parameters() is how an optimiser finds the few thousand tensors to update among the millions in your program. Everything else Modules do (nesting, saving, device movement, train/eval) falls out of the same bookkeeping.

The Part VII project asks you to write parameters() yourself, and describes it as "returns every trainable value, so the optimiser can find them". That sentence is the entire justification for the Module system, and it is worth seeing why the problem is hard enough to need one.

An optimiser must be handed a list of tensors to update. In a fifty-layer network those tensors are scattered across nested objects, some layers have two, some have four, some have none, and a few tensors that look like parameters (a running mean in a normalisation layer, a positional encoding table) must not be updated. Assembling that list by hand is possible once and unmaintainable thereafter.

import torch.nn as nn

model = nn.Sequential(nn.Linear(3, 4), nn.ReLU(), nn.Linear(4, 2))

sum(p.numel() for p in model.parameters())    # 26
[n for n, _ in model.named_parameters()]
### ['0.weight', '0.bias', '2.weight', '2.bias']

Twenty-six numbers: $3{\times}4 + 4$ for the first layer, $4{\times}2 + 2$ for the second. Note that nn.ReLU contributes nothing and is still in the list at index 1, which is a Module with no parameters and a perfectly ordinary thing to be.

Writing one

Two methods, and the rest is inherited:

class MLP(nn.Module):
    def __init__(self, d_in, d_hidden, d_out):
        super().__init__()                    # REQUIRED -- see below
        self.fc1 = nn.Linear(d_in, d_hidden)
        self.fc2 = nn.Linear(d_hidden, d_out)

    def forward(self, x):
        return self.fc2(torch.relu(self.fc1(x)))

model = MLP(20, 64, 2)
model(x)          # calls forward -- never call model.forward(x) directly
Why assignment is doing something invisible

self.fc1 = nn.Linear(...) looks like an ordinary attribute assignment and is not. nn.Module overrides __setattr__: when you assign a Module or a Parameter to an attribute, it is registered in an internal dictionary. That registration is what makes parameters(), state_dict(), .to(device) and .train() able to find it.

Which explains two failures that otherwise look like magic:

  • Forgetting super().__init__() means the internal dictionaries never exist, and the assignment raises or the parameters vanish. It is not ceremony.
  • Putting layers in a plain Python list (self.layers = [nn.Linear(...), ...]) registers nothing, because a list is not a Module. The model runs, trains nothing, and reports zero parameters. Use nn.ModuleList or nn.Sequential, which are Modules that hold Modules.

That second one is a genuinely nasty bug: the forward pass works, the loss decreases slightly because the registered layers still learn, and the unregistered ones sit at their initialisation forever.

And model(x) rather than model.forward(x) because __call__ wraps forward with the hook machinery that other tooling depends on. Calling forward directly usually works and silently bypasses it.

Parameters versus buffers

Some tensors belong to a model, must be saved with it and moved to the GPU with it, and must not be touched by the optimiser. A batch-normalisation running average is the standard example: it is estimated from data, not learned by gradient descent.

self.weight = nn.Parameter(torch.randn(10))       # learned
self.register_buffer("running_mean", torch.zeros(10))  # saved, moved, not learned

The distinction exists because "part of the model" and "updated by the optimiser" are different questions, and the Module system answers them separately.

§9 Composing, and reading someone else's model

Modules nest, and the nesting is what makes large models describable:

model = nn.Sequential(
    nn.Linear(784, 256), nn.ReLU(), nn.Dropout(0.2),
    nn.Linear(256, 64),  nn.ReLU(),
    nn.Linear(64, 10),
)
print(model)        # prints the whole structure, indented

nn.Sequential is the right tool when the data flows straight through. The moment there is a branch, a skip connection or a conditional, you need a real forward, which is why residual networks, per Part VII §18, cannot be written as a Sequential:

def forward(self, x):
    return x + self.block(x)        # the skip of Part VII section 18

One line, and it is the structural change that made very deep networks trainable. It is also exactly the line a purely sequential description cannot express, which is a good illustration of why the framework exposes forward at all rather than only offering layer stacks.

Watch the shapes: reading a model you did not write

Printing a model gives you the layer sizes, and the chaining rule of Part I §5 does the rest: each layer's output width must equal the next one's input width. A model that prints Linear(784, 256) followed by Linear(128, 10) is broken, and you can see it without running anything.

The one that is not visible from the print is the batch axis, which every layer passes through untouched. Part I §6's box on batched matrix multiplication is the fact you need: shapes in a model description describe one example, and every real tensor has one more axis on the left.

§10 Initialisation, which is not decoration

A freshly constructed layer already has values in it, and where those came from is the subject of Part VII §11. This section is about how to see them and change them.

layer = nn.Linear(256, 256)
layer.weight.std()          # about 0.036 -- roughly 1/sqrt(256) = 0.0625, scaled

nn.init.kaiming_normal_(layer.weight, nonlinearity="relu")  # the ReLU scale
nn.init.zeros_(layer.bias)

The defaults are reasonable and not always right. PyTorch initialises nn.Linear from a uniform distribution scaled by $1/\sqrt{\text{fan-in}}$, which is the Part VII §11 derivation for a linear layer. For a ReLU network the correct scale carries an extra factor of $\sqrt{2}$, because ReLU discards half the signal, and the library does not know what activation you intend to put after the layer.

Why this is worth a section rather than a footnote

Initialisation is the clearest case in this book of a default that is invisible, plausible, and capable of preventing a deep network from training at all.

Part VII's Figure 7 measures it: with the scale slightly too small, activations shrink layer by layer until the signal reaching the output is numerically zero; slightly too large and they explode. Neither raises an error. The loss simply refuses to move, or becomes nan, and the symptom looks like a bad learning rate.

For a network of ten layers the default is fine. For fifty it is not, which is why every serious architecture specifies its own initialisation, and why reading a model's reset_parameters is part of reading the model.

Try it

A colleague's model class stores its layers as self.layers = [nn.Linear(64, 64) for _ in range(8)] and iterates over them in forward. The model runs and the loss decreases a little, then plateaus. What is wrong, and what single command would have revealed it in one second?

Answer. A plain Python list registers nothing, so none of those eight layers appear in model.parameters(). The optimiser was never given them, so their weights sit at their random initialisation for the entire run. The loss moved a little because whatever is registered (an output layer, say) still learns, and then it plateaus because it is trying to classify the output of eight frozen random projections.

The diagnostic: sum(p.numel() for p in model.parameters()). It would have reported a number far smaller than the architecture implies. Count your parameters before training anything: it takes one line, it catches this class of bug immediately, and it is also how you notice you have built a model ten times larger than you intended.

The fix is nn.ModuleList, which is a list that is also a Module.
