Everything so far changes the model. This movement changes what the model has access to at the moment it answers, which is usually cheaper, always more current, and increasingly where the capability actually comes from.

§34 Retrieval

Go and read

Lewis et al. (2020), Retrieval-augmented generation. The construction, and the argument for keeping knowledge in a document store rather than in weights: current, attributable, editable and access-controlled. All four are properties a fine-tune cannot have.

The construction

Embed a corpus (Part XV), index it (Part XV §29), retrieve passages relevant to the query, and put them in the context. The model then answers from text in front of it rather than from its weights.

What this buys is specific: knowledge that is current, attributable to a source, correctable by editing a document rather than retraining, and access-controlled per user. None of those is available from a fine-tune, and all of them are what most deployments actually need.

Pitfall: the failure is usually retrieval, and it is usually blamed on the model

A retrieval system has two independent failure points and Part XV §29's separation applies: run exact search on a sample. If exact search does not surface the right passage, the encoder is at fault and no amount of prompting fixes it.

Then the second failure, which is specific to this setting: the model receives a retrieved passage and must decide whether to use it. Given an irrelevant passage it will often use it anyway; given a passage that contradicts its weights it may follow either. Both are measurable by construction (inject a known-irrelevant or known-wrong passage and count), and both are worth measuring before deployment rather than after.

§35 Tools

Emitting a call instead of an answer

Give the model a description of available functions and let it emit a structured call; run it; put the result back in the context. A calculator removes §4's arithmetic problem outright. Code execution replaces a guess with a computation. Search replaces recall with retrieval.

The pattern is worth naming: the model decides what to do and something else does it. It is the same division as Part XVIII §42's verifiable rewards, and it is reliable for the same reason: the hard part is delegated to something that is actually correct.

§36 Agents

The loop, and where it breaks

Let the model call tools, observe results, and decide what to do next, repeatedly. That is the whole idea, and it turns a single prediction into a sequential decision problem: Part XVIII's setting, with a policy that was never trained by Part XVIII's methods.

The failure modes are therefore the ones Part XVIII predicts. Compounding error: at 95% per step, twenty steps is 36%. No credit assignment: a failure at step 20 gives no signal about the mistake at step 3. Distribution shift: after a few steps the context is the model's own output, which is Part XVI §12's exposure bias over a much longer horizon.

What makes agents work in practice is mostly the same as what makes reinforcement learning work: verifiable intermediate steps. An agent that can run tests, check a compiler, or query a database gets a correction signal per step. One that cannot is a twenty-step open-loop plan, and the arithmetic above is what happens to it.

§37 Test-time compute

Spending more at inference instead of at training

Several mechanisms, in rough order of sophistication. Sampling several answers and taking the most common, which works when errors are uncorrelated. Best-of-$n$ against a verifier, which works exactly as well as the verifier does. Longer chains of reasoning, which §22 measures. And models trained to use that budget: Part XVIII §42's reasoning training, where the policy learns to search rather than being prompted to.

The reframing this produced is genuine: performance is a function of training compute and inference compute, and the second can be traded against the first. A smaller model thinking longer can beat a larger one answering immediately, which changes Part XVII §14's lifetime-cost arithmetic substantially.

Pitfall: best-of-$n$ is Part XIV §20 with extra steps

Generating $n$ candidates and selecting the best by a scorer is selection on a noisy measurement, and the winner's score is biased upward exactly as Part XIV §20 measured. If the scorer is a learned reward model, large $n$ finds its errors, Part XVIII §41 again.

So report $n$, and evaluate the selected answer against something the selector did not see. A best-of-64 result compared against a single-sample baseline is not a comparison of models.

§38 Context engineering

What actually goes in the window

In a deployed system the context is assembled: a system prompt, tool definitions, retrieved passages, conversation history, and the request. That assembly is a design problem with its own failure modes.

Three worth knowing. §12's position effect means where you put something changes whether it is used, so the important material goes at the edges. Instruction dilution: a system prompt competing with thousands of tokens of retrieved text loses. And everything in the context is trusted by default, which is the mechanism behind prompt injection: a retrieved document containing instructions is, to the model, indistinguishable from instructions.

That last one is a security property rather than a quality one, and it does not have a clean fix: the model has no channel that separates data from instructions, so the separation must be enforced outside it.
