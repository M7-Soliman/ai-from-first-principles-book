Part DData, batching, devices

§11 Dataset and DataLoader

In 60 seconds

A Dataset answers two questions: how many examples are there, and give me number $i$. A DataLoader wraps one and produces shuffled batches. That is the whole abstraction, and it is deliberately small: the split exists so that the batching logic can be written once for every dataset that will ever exist.

Part III §14 established why we train on minibatches: the gradient is an average, an average can be estimated by sampling, and the estimate costs a fixed amount regardless of dataset size. This section is the plumbing that supplies those samples.

from torch.utils.data import Dataset, DataLoader, TensorDataset

# the two-method interface, in full
class MyDataset(Dataset):
    def __len__(self):          return len(self.items)
    def __getitem__(self, i):   return self.x[i], self.y[i]

# when your data is already tensors, use the built-in
ds = TensorDataset(X, y)
dl = DataLoader(ds, batch_size=64, shuffle=True)

for xb, yb in dl:               # xb is (64, ...), yb is (64,)
    ...

The division of labour is the point. A Dataset knows how to produce one example (read a file, decode an image, tokenise a sentence) and knows nothing about batching, shuffling or parallelism. The DataLoader knows all of those and nothing about your data. Write the first, get the second free.

Why shuffle=True is not cosmetic

Part II §17 defined the empirical distribution (a Dirac spike on each training point, each with weight $1/m$) and observed that sampling from it means picking a training example uniformly at random. shuffle=True is that sentence implemented.

Turn it off and the "random" sample of Part III §14 is not random: you get the data in whatever order it was stored. If that order is meaningful (sorted by class, by date, by source, which is extremely common), then each batch is drawn from a different distribution, the gradient estimate is no longer unbiased, and the model spends each epoch overfitting whichever region it is currently passing through.

The symptom is a loss curve that oscillates on a period matching the epoch length. If you see that, check the shuffle flag before anything else.

The arguments that matter

batch_sizePart III §14's $b$: the noise/cost trade

That figure is the practical argument behind a claim made twice already. Part I said batching exists because matrix-matrix multiplication is matrix-vector multiplication done to several vectors at once; Part III said the accuracy bought by a large batch is mostly wasted. Together they imply a batch should be as large as the noise budget and memory allow, and Figure 3 is why the lower bound is not 1.

§12 Devices

A tensor lives somewhere, and operations require their operands to live in the same place. There is no automatic transfer, and the refusal is deliberate: moving data between main memory and an accelerator is slow enough that doing it silently, inside a loop, would destroy performance in a way nobody could see.

device = torch.device("cuda" if torch.cuda.is_available() else "cpu")

model = model.to(device)          # moves every parameter and buffer

for xb, yb in dl:
    xb, yb = xb.to(device), yb.to(device)   # and the data, every batch
    ...
Pitfall: the model moves once, the data moves every batch

The asymmetry catches everyone. model.to(device) is called once because parameters persist; xb.to(device) is called every iteration because each batch is a new tensor freshly produced by the loader.

Move the model and forget the data and you get RuntimeError: Expected all tensors to be on the same device. It is one of the clearer messages the library produces, and §16 lists it with the rest.

Note also that model.to(device) modifies the model in place and returns it, while tensor.to(device) returns a new tensor and leaves the original alone. So xb.to(device) on its own line does nothing at all: you must assign the result. This inconsistency is a genuine wart, and it is the single most common device bug.

Two habits make device handling painless. Define device once at the top of the script and refer to it everywhere, rather than writing "cuda" in a dozen places, so the script then runs unchanged on a laptop. And create tensors on the right device in the first place, torch.zeros(n, device=device), rather than creating them on the CPU and moving them.

Why the GPU is where all of this is going

Part I §1 said the reason matrices dominate is hardware: a GPU is in essence a machine built to multiply matrices very fast in parallel, and that expressing a computation in that form is what makes it affordable.

Devices are where that claim becomes an API. Every design decision in this part points the same way: batching exists so the work is matrix-shaped, dtypes are 32- or 16-bit so more of it fits, transfers are explicit so you cannot accidentally spend your time moving bytes instead of multiplying them. The framework is an interface to that hardware, and the parts of it that feel arbitrary are usually the parts where the hardware is showing through.

Try it

This evaluation loop is correct on a CPU and fails on a GPU. Find both bugs.

model.to(device)
for xb, yb in val_dl:
    xb.to(device)
    total += (model(xb).argmax(1) == yb).sum()

Answer. First: xb.to(device) returns a new tensor and discards it. The line has no effect, xb is still on the CPU, and model(xb) raises a device mismatch. It must be xb = xb.to(device).

Second: even once that is fixed, yb was never moved, so the comparison == yb compares a GPU tensor against a CPU one and raises the same error one line later.

A third thing is not an error but is wrong anyway: there is no with torch.no_grad(), so this loop builds a full graph for every batch and retains it inside total, exactly the leak of §7's Try it. Correct, slow, and eventually out of memory.
