Part FWhen it breaks

§16 Error messages, decoded

In 60 seconds

Almost every runtime error in PyTorch is one of five things: a shape that does not chain, a dtype that does not match, a device that does not match, a graph that was already freed, or a gradient that was never requested. Each has a characteristic message, and each maps back to something derived earlier in this book.

Every message below is real output, reproduced verbatim. They are worth reading once now so that the first time you meet one it is recognition rather than search.

Shape errors

RuntimeError: mat1 and mat2 shapes cannot be multiplied (8x7 and 10x5)

What happened. Part I §5's chaining rule was violated: the inner dimensions did not agree. You fed an input of width 7 into a layer built for width 10.

Why the numbers look wrong. This message causes real confusion, because nn.Linear(10, 5) stores its weight with shape $(5, 10)$ (output first, per the box in Part I §8), and the message reports it as 10x5, already transposed for the multiplication. So neither number is the shape you typed. Read it as: your data is $8\times7$, the layer wants something $\ast\times10$, and $7 \neq 10$.

The fix is almost never at the line that raised. The mismatch was introduced earlier: a flatten that produced the wrong width, a layer size that did not get updated when the input changed. Print shapes backwards from the failure until you find the first one that surprises you.

dtype errors

RuntimeError: mat1 and mat2 must have the same dtype, but got Double and Float
RuntimeError: expected scalar type Long but found Double

The first is §2's NumPy-versus-PyTorch default: float64 data meeting float32 weights. Fix with X = X.float().

The second is the opposite direction and comes from a loss function. cross_entropy wants class indices, which are integers (Part II §25 explained why): it looks up one element rather than forming a one-hot vector. Fix with y = y.long().

Note the asymmetry, because it is the thing to remember: features want floats, labels want integers. Loading both the same way guarantees one of them is wrong.

Device errors

RuntimeError: Expected all tensors to be on the same device,
but found at least two devices, cuda:0 and cpu!

The clearest message the library produces, and by §12 the usual cause is xb.to(device) written without assigning the result: the call returns a new tensor and the original is untouched.

Graph errors

RuntimeError: Trying to backward through the graph a second time
(or directly access saved tensors after they have already been freed).

Section 6: the first backward() freed the saved activations. Either you genuinely need two backward passes (pass retain_graph=True), or, far more often, a tensor from a previous iteration is still attached to the graph and being reused. The second case is the accidental-accumulation bug of §3, and retain_graph=True will "fix" it by leaking memory instead. Check which you have before reaching for the flag.

RuntimeError: one of the variables needed for gradient computation
has been modified by an inplace operation ... is at version 1;
expected version 0 instead.

Section 7's version counter. Some operation saved a value for its backward pass and something overwrote it. Find the underscore-suffixed method (relu_, add_, clamp_, or a x[mask] = 0 assignment) and make it out-of-place.

Gradient errors

RuntimeError: element 0 of tensors does not require grad
and does not have a grad_fn

You called backward() on something with no history. Either the computation happened inside torch.no_grad(), or a detach() severed the chain, or the parameters were never marked; §8's plain-Python-list bug produces exactly this.

RuntimeError: grad can be implicitly created only for scalar outputs

You called backward() on a tensor with more than one element. A loss must be a single number, because the gradient is with respect to one scalar (Part 0 §23's gradient is defined for a scalar-valued function). The usual cause is a missing reduction: F.cross_entropy(..., reduction="none") returns one loss per example, and someone forgot the .mean().

The error is really asking you to supply what a scalar loss would have supplied implicitly: a starting gradient, one number per output. Passing one explicitly (y.backward(gradient=v)) is not a workaround, it is the general case, a vector-Jacobian product rather than a scalar one. You will meet it reading library code that backpropagates through something non-scalar on purpose (per-example gradients, a custom loss surface); no error, because the shape was supplied.

§17 The debugging order

Part VII §20 gives the diagnostic order for a training run that is not working. This is its counterpart for a program that is not running, and for the harder case: one that runs and is wrong.

When it does not run
  1. Read the last line of the traceback, not the first. The first is your code; the last is the operation that actually failed.
  2. Print shapes. Working backwards from the failure until one surprises you finds the cause in most cases, and it costs a minute.
  3. Print dtypes and devices for the two operands named in the message.
  4. Check parameter count (sum(p.numel() for p in model.parameters())) against what the architecture implies.
When it runs and is wrong
  1. Overfit ten examples. Part VII §20's test, and still the most informative thing available. If a model cannot drive the loss to near zero on ten examples it has a bug, not a generalisation problem.
  2. Is the gradient non-zero? Print p.grad.norm() for a parameter after backward(). None means it is not in the graph; zero means the path is broken; nan means an overflow upstream.
  3. Is every parameter in the optimiser? Compare the counts. This catches §8's unregistered-layer bug.
  4. Are train() and eval() in the right places? §14.
  5. Is the data what you think? Print one batch. Look at the labels. Check the range of the features. A surprising number of "model" bugs are label misalignment.
Why the ordering is the same as Part VII's

Both lists are sorted by how cheaply a cause can be ruled out, and for the same reason: a bug that masquerades as a modelling problem will absorb days.

The distinctive hazard of a framework is that it makes wrong programs run. A shape bug raises immediately; a broadcasting bug produces a plausible tensor, a mode bug produces plausible numbers, an unregistered layer produces a model that trains a bit. All three look like "the approach is not working", and none of them is.

So the discipline is to verify the mechanical things first (shapes, gradients, parameter counts, modes) before forming any opinion about the model. Ten minutes of checks against a week of tuning something that was never connected.

Try it: the last one

Training loss decreases smoothly for three epochs and then becomes nan and stays there. Give the order in which you would check things, and say what each check rules out.

Answer. First, lower the learning rate and see whether it survives. Part III §9 gave the stability bound $\alpha < 2/\lambda_{\max}$; exceeding it diverges, values leave float range, and by Part III §2 inf arithmetic produces nan, which then contaminates everything. This is the most common cause by a wide margin and the cheapest to test.

Second, check for a log of zero. If you computed a softmax and then took its log rather than using cross_entropy on logits, an underflowed probability gives $\log 0 = -\infty$ (Part II §25's fused-loss pitfall exactly). The tell is that it appears suddenly rather than growing, because underflow is a cliff and divergence is a ramp.

Third, check the data for a nan or an infinity in the inputs. One bad row poisons the batch it lands in, which explains why it took three epochs to appear: that row had not been sampled yet.

Fourth, add gradient clipping (Part I §15). If the run survives with clipping and dies without, the problem is occasional large gradients rather than a systematically wrong rate, and clipping is the correct fix rather than a workaround.

The ordering is by cost, and the first two account for the large majority.
