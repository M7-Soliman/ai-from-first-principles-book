Before you start

This part is different from the three before it. Those derived mathematics that will be true in fifty years. This one describes a library, and libraries change.

It is here anyway, and placed exactly here, for a reason worth stating.

Everything a training loop contains has now been built from nothing. The chain rule is Part 0 §17. The matrix arithmetic of a layer is Part I §§4–8, hand-computed. Cross-entropy was derived from maximum likelihood in Part II §26, not asserted. Stochastic gradient descent, momentum and Adam are Part III §§14–17, with the formulas worked out and the figures measured. There is no line in a modern training script whose mathematics you have not already seen.

That is the only honest moment to introduce a framework. Earlier and you would be copying incantations: F.cross_entropy would be a magic word rather than a consequence. Later and you would have spent three more parts writing NumPy that nobody writes.

What this part is not

It is not a tutorial that gets you to a working model as fast as possible. Those exist, they are good, and they are not what a book like this is for.

The aim here is different: to make the framework legible rather than usable. Every section takes something the library does, connects it to the mathematics that forces it, and then shows what happens when the connection is broken. By §17 you should be able to read an unfamiliar training script and say what each line is for, and, more usefully, to look at an error message and know which of the derivations behind it has been violated.

The material that dates fastest is quarantined into this one part deliberately. If a future version of PyTorch renames something, nothing in Parts 0 through III needs a word changed.

§0.1 Why PyTorch

Two libraries have dominated for most of this book's life, and the choice between them matters less than either community suggests. This book uses PyTorch for three reasons.

It is dominant in research, so the papers you will read in the reading list ship PyTorch code. Its API sits closest to the notation: a @ b is a matrix product, x.T is a transpose, and a model is a Python object you can print and step through with an ordinary debugger. And its graph is built as the code runs, which means the graph in §4 is the one your program actually executed rather than one compiled in advance from a description.

TensorFlow, and Keras layered on top of it, does the same things with different vocabulary. Where a difference would genuinely catch you out (a transposed weight matrix, an unsafe default), this part says so. It does not attempt a full translation, because a half-remembered second API is worse than one you know.

A third, JAX, has earned a place in research code since: composable function transforms (grad, vmap, jit) over pure functions, rather than an object that owns state. The mathematics you have built transfers directly (a transform is still the chain rule under the name), but its idioms are different enough from the object-oriented shape below that this part leaves it unmapped rather than half-covering it.

Pitfall: versions

Everything here was run against PyTorch 2.x, and the numbers printed in the output comments are real output from that version. Function names in the core (tensor, backward, nn.Module, optim) have been stable for years and are safe to learn. The periphery moves.

Where a snippet's exact output could drift, this part says what to expect rather than quoting a digit.

§1 A complete program, line by line

In 60 seconds

A training script is four objects (data, model, loss, optimiser) and a loop that repeats five statements. Everything else in this part is detail about one of those nine things. Read the program first; the sections that follow open it up.

Here is a working, complete program. It trains a classifier, evaluates it, and saves it. Nothing is elided.

import torch
import torch.nn as nn
import torch.nn.functional as F
from torch.utils.data import TensorDataset, DataLoader

torch.manual_seed(0)

# ---- data -------------------------------------------------------------
X = torch.randn(2000, 20)
y = (X[:, :3].sum(dim=1) > 0).long()          # a learnable rule

n_tr, n_va = 1400, 300
train_ds = TensorDataset(X[:n_tr], y[:n_tr])
val_X, val_y = X[n_tr:n_tr+n_va], y[n_tr:n_tr+n_va]

train_dl = DataLoader(train_ds, batch_size=64, shuffle=True)

# ---- model ------------------------------------------------------------
model = nn.Sequential(
    nn.Linear(20, 64),
    nn.ReLU(),
    nn.Linear(64, 2),
)

# ---- optimiser --------------------------------------------------------
opt = torch.optim.AdamW(model.parameters(), lr=1e-3)

# ---- loop -------------------------------------------------------------
for epoch in range(10):
    model.train()
    for xb, yb in train_dl:
        opt.zero_grad()                       # 1. clear last step's gradients
        logits = model(xb)                    # 2. forward
        loss = F.cross_entropy(logits, yb)    # 3. how wrong
        loss.backward()                       # 4. backward
        opt.step()                            # 5. update

    model.eval()
    with torch.no_grad():
        acc = (model(val_X).argmax(dim=1) == val_y).float().mean()
    print(f"epoch {epoch}  val acc {acc:.3f}")

torch.save(model.state_dict(), "model.pt")

That is the whole thing. Roughly thirty lines, and it is structurally identical to a script training a model a thousand times larger: the differences are the shape of the data, the contents of the model, and how many machines are involved.

Seeding is necessary, not sufficient: torch.manual_seed(0) fixes the initial weights and the shuffle order, but several GPU kernels (convolutions in particular) pick a fast algorithm nondeterministically unless you also set torch.backends.cudnn.deterministic = True, which costs speed. On CPU, as in this program, seeding alone is enough.

§2 The tensor

Go and read

Micikevicius et al. (2018), Mixed precision training. What it takes to train in 16 bits safely: loss scaling to keep small gradients out of the subnormal range, and a 32-bit copy of the weights so that tiny updates are not rounded away. It is Part III §1's precision-versus-range trade at production scale, and it explains why bfloat16 later displaced the float16 scheme described here.

Part I §2 introduced the tensor as the four-rung ladder of scalar, vector, matrix and array. That is what it holds. Here is what it is as an object, because five attributes explain most of what goes wrong.

t = torch.randn(32, 64)

t.shape      # torch.Size([32, 64])  -- the maths
t.dtype      # torch.float32        -- the precision
t.device     # cpu                  -- where the bytes live
t.requires_grad  # False            -- is this being differentiated?
t.grad       # None                 -- and the result, once there is one

Those five are worth memorising as a checklist, because when something fails it is almost always one of them. Two tensors will not multiply if the shapes do not chain. They will not add if the dtypes differ. They will not do anything at all if they are on different devices. And no gradient will appear if requires_grad was never set.

Watch the shapes: the habit, now with a debugger

Part I §0.4 asked you to write down a shape before computing anything. In a framework that habit becomes cheaper and more important: cheaper because print(t.shape) costs nothing, more important because a wrong shape frequently does not raise: broadcasting silently produces a plausible tensor of the wrong size.

The single most useful debugging line in deep learning is a shape printed at the point you stopped being sure.

dtype, and the default that will bite you

Part III §1 established the trade between precision and range. Here is where it becomes a decision you make by accident:

torch.tensor([1.0, 2.0]).dtype     # torch.float32  -- note: not 64
torch.tensor([1, 2]).dtype         # torch.int64    -- no decimal point, no float
np_array_converted = torch.from_numpy(a)  # inherits NumPy's float64!

Three defaults, three different answers. Writing 1.0 gives you 32-bit; writing 1 gives you an integer, which will refuse to enter a linear layer; converting from NumPy gives you 64-bit, which will then refuse to combine with the 32-bit weights of your model. All three produce error messages, and §16 decodes them.

Pitfall: NumPy is 64-bit and PyTorch is 32-bit

This mismatch catches everyone once. A dataset loaded with NumPy arrives as float64; a model's parameters are float32; multiplying them raises RuntimeError: mat1 and mat2 must have the same dtype, but got Double and Float.

The fix is one call (X.float()), and the reason to know it is that the error names the symptom rather than the cause. The libraries chose different defaults for good reasons: NumPy is for numerical computing, where Part III §5's condition numbers can be large; PyTorch is for training, where speed matters more than digits.

§3 Getting numbers in and out

A tensor is not a number, and the boundary between them causes a specific and very common class of bug.

loss = torch.tensor(0.42, requires_grad=True)

loss.item()          # 0.42        -- a Python float. Use this.
float(loss)          # 0.42        -- same thing
t.tolist()           # nested Python lists
t.detach().numpy()   # a NumPy array sharing the same memory

.item() works only on a single-element tensor, which is exactly what a loss is. The reason to reach for it is not convenience.

Why .item() matters: the accidental memory leak

Consider the innocent-looking line inside a training loop:

total_loss += loss

loss is a tensor with a grad_fn, so it is attached to the entire computational graph of that batch, every activation and every intermediate value. Adding it to a running total keeps that graph alive. Do it for a thousand batches and you are holding a thousand graphs, and the run dies with an out-of-memory error that points at whichever batch happened to be last.

The fix is total_loss += loss.item(), which extracts a plain float and lets the graph be freed. This is one of the most common bugs in real training code, it scales with how long you train, and it looks nothing like a memory problem in the source.

Section 6 explains what the graph is holding and why it is expensive; Figure 2 measures it.

Try it

You load features with X = np.loadtxt("data.csv") and labels with y = np.loadtxt("labels.csv"), convert both with torch.from_numpy, and pass them to a model with an nn.Linear first layer and F.cross_entropy as the loss. Name the two errors you will hit, in order.

Answer. First, X is float64 from NumPy while the layer's weights are float32: RuntimeError: mat1 and mat2 must have the same dtype, but got Double and Float. Fix with X = X.float().

Second, y is also float64, but cross_entropy wants class indices (integers), as Part II §25 explained, because it looks up one element rather than forming a one-hot vector. So you get RuntimeError: expected scalar type Long but found Double. Fix with y = y.long().

Two different dtype errors from one loading pattern, requiring opposite conversions. Neither is a deep problem and both cost a beginner an afternoon, which is why they are in §16's table.
