Part DTabular practice

The book has cited the finding that trees beat deep learning on tables since Part VI and never run it. This movement runs it, finds the answer depends on the generating process rather than on the format, and then covers the two things that decide a tabular project more than the model family does: whether the probabilities mean anything, and whether the validation is honest.

§25 Are the scores probabilities

The question, and why the answer differs by method

Part XIV §5 asked whether predicted probabilities match observed frequencies, and Part XXIV built the machinery. For tree ensembles the answer depends entirely on what was optimised.

Gradient boosting with the logistic loss is minimising a proper scoring rule (a loss whose minimiser is the true conditional probability), so calibration is what it was fitted for. A random forest's output is the fraction of trees voting for a class, which was never fitted to anything and is a vote share rather than an estimate.

What the argument promises, and what it does not

The proper-scoring-rule argument is a statement about the population optimum: if fitting reached the loss's exact minimiser, the output would be the true probability. Regularisation, early stopping and a finite training set all keep the fitted function short of that minimiser, and the argument itself says nothing about how far short; it is a claim about what the loss is optimising for, not a guarantee about what any particular fit achieves.

Niculescu-Mizil & Caruana (2005) measured the gap directly and found boosted trees on real data frequently miscalibrated (most severely under AdaBoost's exponential loss, and to a real if smaller degree under log-loss), which is why post-hoc calibration is routine practice for boosted models rather than a precaution for the occasional bad fit. Figure 6's 0.018 below is a genuine measurement and a good one, but of one well-specified population on one synthetic generator: evidence that boosting can come out calibrated when it optimises the right loss, not that it reliably does on a dataset you have not checked.

§26 Measured

Pitfall: calibrating on the training set

Fitting the calibrator on the same rows the model was fitted on gives a calibrator fitted to the model's memorised residuals, and it will look excellent in training and do nothing in production. Isotonic regression is flexible enough to make this failure invisible.

Use a dedicated split, exactly as Part XXIV §24's conformal calibration does, and for the same reason.

§27 The comparison this book has been owing

How to run it so the answer means something

Three requirements, each of which is routinely skipped by whichever side is publishing.

Tune both families. An untuned baseline is how this comparison is usually won. Both families here get the same small grid and the same validation split.

Repeat it. One split gives one number with no error bar, and reporting a ratio off it is reporting noise.

Pair the comparison. Give both families the same draws, so the difference is measured within a repetition rather than between them.

§28 Which family wins, and when

Go and read

Grinsztajn, Oyallon & Varoquaux (2022), Why do tree-based models still outperform deep learning on typical tabular data?. The paper Part VI §16 cited and this movement finally runs. Read past the headline for the ablations: the gap tracks whether the target function is smooth or irregular and how many features are uninformative, which is a claim about the generating process, not about tables as a format. Why each wins where it does

A tree represents a threshold exactly and a hyperplane as a staircase. A network is the other way round. So a target assembled from indicator functions is the tree's native language, and a linear combination is the network's.

The three-way product is the interesting case. A depth-3 tree can express a 3-way interaction in principle, and it must partition the input space to do so, spending leaves on regions where a smooth function would interpolate. Trees get interactions but pay for them in data.

The practical reading: the folk claim is not that trees suit tables, it is that real tabular targets tend to be built out of thresholds and low-order interactions, which is a claim about the world, and one worth checking on your own data rather than inheriting.

§29 Validation, which matters more than the model

What to split on, in order of how often it is got wrong

Time. If the rows have a date and the model will be used on future rows, split chronologically. §36 measures what a random split is worth here and it is a great deal.

Groups. If rows share an entity (a user, a patient, a device), split on the entity, or the same entity appears on both sides and the model is scored on rows it has partly seen.

Duplicates. Near-duplicate rows across a split do the same thing. Part XIII §15's near-duplicate detection is the instrument.

Everything else: the encoders of §20, any statistic computed over the full table, any imputation fitted before splitting. Every preprocessing step belongs inside the fold.

§30 When to use which

An honest decision procedure

Start with gradient boosting. It needs no scaling, handles mixed types and missing values, tunes over one effective hyperparameter, and is a strong baseline on almost any table.

Reach for a network when the target looks smooth or additive in the features, when there is a lot of data, when part of the input is text or an image, or when you need embeddings for something else downstream.

Reach for a linear model when you need the coefficients to be inspectable and defensible, which is more often than this book's other parts imply.

Ensemble them if the budget allows. Boosted trees and a network make different errors, which is exactly the condition under which averaging helps.
