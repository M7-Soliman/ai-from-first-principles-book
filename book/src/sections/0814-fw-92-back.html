BuildThe project

Six to eight hours. Unusually for this book, the project is not to build something: it is to break something, repeatedly, on purpose, and learn to recognise the wreckage.

P.1 What you are building

brokenrepo: a working training script, and then eleven deliberately sabotaged copies of it, each with a single bug from this part.

The rule: you must diagnose each one from its symptoms before looking at the diff. Run it, observe, form a hypothesis, check the hypothesis, and only then read the change. Write down what you predicted and whether you were right.

P.2 Stage 1: the working baseline

Write a clean training script for a small classification problem. It must include, and you must be able to justify, every line:

  • A Dataset and a DataLoader with shuffle=True.
  • A model written as a nn.Module subclass, not a Sequential.
  • train() / eval() switching, and no_grad() for evaluation.
  • A parameter count printed before training starts.
  • Train, validation and test splits, with the test set touched exactly once (Part VI §9).
  • A checkpoint saving model, optimiser and epoch.

Deliverable: a run that reaches a sensible accuracy, plus a bootstrap interval on the final test number using Part V §10. A point estimate alone does not count.

P.3 Stage 2: the eleven bugs

Make eleven copies. Introduce exactly one fault in each, run it, and record the symptom before diagnosing.

Deliverable: a table with three columns (symptom observed, hypothesis, actual cause) and an honest count of how many you got right first time. Most people get six or seven. The ones people miss are usually 2 versus 3, and 6.

P.4 Stage 3: instrument it

Return to the working version and add the diagnostics of §17, so that the next real bug announces itself:

  • Parameter count, printed once, compared against what the architecture implies.
  • Gradient norm, printed every $N$ steps. Watch for None, exact zero, and nan: three different failures, per drill C18.
  • A tiny-sample overfitting test: ten examples, trained until the loss is near zero, run automatically before the real training starts. If it fails, stop.
  • Shapes of the first batch, printed once.

Deliverable: reintroduce bugs 1, 4 and 7 and confirm your instrumentation catches each before the run finishes.

P.5 Stage 4: measure the machine

Reproduce this part's figures on your own hardware. They will differ, and the differences are the interesting part.

  1. The graph. Walk grad_fn for your model and print every node. Count the AccumulateGrad nodes and check it equals your parameter tensor count.
  2. Memory. Sum the saved activations against batch size. Confirm linearity.
  3. Throughput. Time a step across batch sizes. Find where your curve flattens.
  4. Modes. Forward one input 2,000 times in each mode; report both spreads.

P.6 Stretch

  • Gradient accumulation. Verify that four batches of 32 with accumulation give the same gradient as one batch of 128, to floating point tolerance. This is a real test and it catches the missing division.
  • A custom autograd.Function with a hand-written backward, verified with gradcheck. This is the Part VII project's Value class, wearing the library's interface.
  • Mixed precision. Run in bfloat16 with autocast and measure both the speedup and the change in final accuracy. Part III §1 predicts which one is large.
  • Freeze and fine-tune. Train a model, freeze all but the last layer with requires_grad_(False), and confirm from the parameter count and the gradient norms that only the head is moving.

P.7 Done when

  • The baseline trains, and every line in it can be justified.
  • All eleven bugs diagnosed, with your first-guess accuracy recorded honestly.
  • Instrumentation catches bugs 1, 4 and 7 automatically.
  • The four figures reproduced on your hardware.
  • A bootstrap interval on the final test accuracy.
  • Your notes name one thing the framework does that you had previously assumed was magic.
Why this project, rather than building something

Every other project in this book asks you to construct a thing from nothing, because construction is how you learn what a thing is. This one is different because the skill it targets is different.

You will spend far more of your working life reading failures than writing new implementations. A framework's characteristic hazard, per §17, is that it happily runs wrong programs, and the three most expensive bugs in this part (the unregistered list, the missing eval(), the double softmax) all produce plausible numbers rather than errors. The only defence is to have seen each symptom once, deliberately, when you already knew the answer.

Doing it on purpose costs an afternoon. Meeting them for the first time inside a real project costs considerably more, and you will not have the luxury of knowing that a bug is what you are looking for.

The one thing to carry forward

The framework records what your code did, and everything else follows from that recording.

Gradients accumulate because a value used twice must receive both contributions. The graph is freed because holding it costs memory that scales with batch and depth. Activations are saved because local derivatives need forward values. In-place operations are version-counted because sometimes they destroy one of those values and sometimes they do not. Modules exist so that the few tensors worth updating can be found among the millions that are not.

Not one of those is an arbitrary API decision. Each is forced by something derived in Parts 0 through III, which is why this part could be short, and why it was worth waiting until now to write it.
