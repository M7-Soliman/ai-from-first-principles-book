BuildThe project

Ten to fourteen hours. You build a cost model from arithmetic, then measure a real system against it, and find the places where the FLOP count and the stopwatch disagree.

P.1 What you are building

serve: an inference cost model, four compression techniques applied to one model, and a measurement harness that reports time rather than arithmetic.

The rule: predict every number before measuring it. This part's claim is that inference cost is largely computable in advance, and the only way to find out whether that is true for your setup is to commit first.

P.2 Stage 1: the cost model

  1. Arithmetic intensity, the ridge point, and which side of it each operation sits on.
  2. KV cache size, the context at which it equals the weights, and concurrent sequences for a device size you pick.
  3. Predicted decode tokens per second from bandwidth alone.
  4. The end-to-end request cost, separating prefill from decode.

Deliverable: one function taking a configuration and returning predicted latency, throughput and cost per token. Then predict all of them for the model you are about to use.

P.3 Stage 2: measure against it

  1. Run the model. Measure time to first token and time per output token, at several batch sizes.
  2. Compare each to the prediction and report the ratio.
  3. Find the batch size at which throughput stops rising, and compare to the predicted ridge.

Deliverable: the predicted-against-measured table. The term you got most wrong is the term your model handles worst, and fixing it is worth more than any optimisation in the rest of the project.

P.4 Stage 3: quantization

  1. Implement per-tensor, per-channel and per-group symmetric quantization.
  2. Sweep bits from 8 down to 2, measuring both weight error and model loss. Plot both and compare their shapes.
  3. Detect the outlier channels. Quantize with the scales computed excluding them and compare, then repeat the version that quantizes everything first and overwrites, and confirm it does almost nothing.
  4. Count the scale storage and report effective bits per weight.

Deliverable: the two curves, the outlier comparison, and the honest bits-per-weight for each scheme.

P.5 Stage 4: sparsity, timed

  1. Magnitude-prune to several sparsity levels, fine-tuning after each. Plot accuracy against sparsity.
  2. Then time the pruned model: as a dense array with zeros, and with a sparse kernel.
  3. Compute dense against sparse storage and find the crossover.
  4. Implement 2:4 and compare its accuracy cost to unstructured at the same 50%.

Deliverable: one plot with three lines: accuracy, measured speedup, and the speedup the FLOP count promised. The gap between the last two is the stage's point.

P.6 Stage 5: distillation and adaptation

  1. Distil your model into a student half the size. Then train the same student directly, as the control.
  2. Sweep temperature and report the teacher's output entropy at each.
  3. Fine-tune fully, take the SVD of the weight deltas, and report the rank for 90% and 99% of the energy.
  4. Then fine-tune with LoRA at several ranks and compare quality at matched trainable parameters.

Deliverable: the distillation gap against the control, and the rank table. Predict the LoRA rank you will need from the SVD, then check whether that prediction held.

P.7 Stage 6: serving

  1. Simulate a queue with a realistic spread of generation lengths. Compare static and continuous batching on throughput and p95 latency.
  2. Compute cache waste under maximum-length reservation and under paging.
  3. Implement speculative decoding with the exact rejection rule. Measure the acceptance rate for drafts of several sizes and compute the implied speedup.
  4. Verify the output distribution is unchanged.

Deliverable: the throughput and latency numbers, and the draft size that maximises the product of acceptance and cheapness.

P.8 Stretch

  • GPTQ in miniature: column-by-column with error compensation, against independent rounding.
  • Cache quantization, keys and values separately, over a long generation.
  • Multi-adapter serving: one base, many LoRAs, one batch.
  • Stack everything and measure the order dependence.
  • Disaggregation: prefill and decode as separate services.

P.9 Done when

  • Your cost model predicts throughput within a factor of two, and you know which term is worst.
  • You have the weight-error and loss curves side by side, and can say why one misleads.
  • You have measured the outlier effect both ways, and know why one of them does nothing.
  • You have timed sparsity rather than counting its FLOPs.
  • You have the distillation control, not just the distillation result.
  • You have the SVD rank table with both 90% and 99%.
  • You have measured speculative decoding's acceptance rate and confirmed the output is unchanged.
  • Your README names one number you predicted wrongly by more than a factor of two.
Why this project

Stage 2 is the reason for the ordering. Almost everything in this part is arithmetic, and arithmetic is either right or it is not, but only a measurement tells you which terms your model is missing. A cost model that predicts within a factor of two is worth more than any single optimisation, because it tells you which optimisation to attempt.

Stage 4 is the second reason. The claim that unstructured sparsity does not speed anything up contradicts a great deal of published arithmetic, it takes ten lines to check, and checking it once permanently changes how you read a compression result.

The one thing to carry forward

Generation is limited by memory bandwidth, not by arithmetic.

Quantization works because it moves fewer bytes. Unstructured sparsity does not work because it removes arithmetic that was not the constraint. Batching is the largest lever because it amortises one weight read across many sequences. Speculative decoding works because a memory-bound pass has arithmetic to spare. The KV cache matters because it competes for the same bandwidth and the same memory.

And the discipline that goes with it: measure time, not FLOPs. The flat line in Figure 5 took ten lines of code and contradicts a great deal of published arithmetic about how much faster a sparse model ought to be.
