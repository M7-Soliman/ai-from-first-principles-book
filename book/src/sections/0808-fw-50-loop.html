Part EThe loop

§13 Five statements, in order

Everything assembles here. The loop is five statements, and each has a derivation behind it and a characteristic failure in front of it.

for xb, yb in train_dl:
    opt.zero_grad()                        # 1
    logits = model(xb)                     # 2
    loss   = F.cross_entropy(logits, yb)   # 3
    loss.backward()                        # 4
    opt.step()                             # 5
What it doesIf you omit it
1 zero_grad clears .grad, which otherwise accumulates (Part VII §21) you step on the sum of every batch so far; loss diverges within ~50 steps
2 forward runs the model, building the graph of §5 n/a
3 loss one scalar: Part II §26's negative log-likelihood a non-scalar cannot be differentiated: see §16
4 backward reverse traversal, filling every .grad gradients stay None; the optimiser does nothing
5 step applies the update of Part III §16 gradients are computed and discarded; loss never moves

The last two failures are worth distinguishing because they look identical from outside (a loss that does not move) and have opposite causes. Forgetting backward() means there is nothing to step on; forgetting step() means there is something and you ignored it. Printing one gradient norm separates them in a second.

Pitfall: the order of 1 and 5 is not free

zero_grad() may go at the top of the loop or immediately after step(), and both are correct. What is not correct is putting it between backward() and step(), which erases the gradients you just computed and turns the optimiser into an expensive no-op.

Put it first. It reads as "begin a fresh accumulation", which is what it is.

Gradient accumulation, which is the exception that proves the rule

Occasionally you want a batch larger than memory allows. The accumulation that zero_grad normally guards against is exactly the mechanism:

for i, (xb, yb) in enumerate(train_dl):
    loss = F.cross_entropy(model(xb), yb) / accum_steps
    loss.backward()                        # adds into .grad
    if (i + 1) % accum_steps == 0:
        opt.step()
        opt.zero_grad()                    # only now

Four batches of 32 accumulate into the gradient of one batch of 128, at a quarter of the memory. The division by accum_steps matters: the loss is a mean over the batch, so summing four means gives four times the intended gradient unless you scale.

Note what this reveals. The += that Part VII §21 justified on correctness grounds (a value used twice must receive both contributions) turns out to also be the mechanism that lets a large model train on a small card. One design decision, two unrelated payoffs.

§14 train() and eval()

Two layers behave differently during training and evaluation, and the model has to be told which it is doing.

Layertrain()eval()
Dropoutrandomly zeroes unitsdisabled entirely
BatchNormuses this batch's statistics, updates running averagesuses the stored running averages
Why this is the most under-reported bug in the field

The failure has three properties that make it unusually expensive.

It is silent. No error, no warning, and the numbers look plausible.

It is biased downward. Evaluating with dropout active means evaluating a crippled model, so your reported accuracy is worse than the truth, which is the direction that makes you distrust a model that was fine, and go looking for problems that do not exist.

It is not reproducible. Two evaluation runs of the same checkpoint give different answers, and the natural conclusion (that something is wrong with the data pipeline) is wrong.

Given Part V §16's insistence on paired comparisons and intervals, note what this does to a comparison: it adds a variance term to one model and not necessarily the other, and no amount of bootstrapping will reveal it because the bootstrap resamples the test set, not the dropout mask.

The discipline is unglamorous and absolute: model.train() at the top of every training epoch, model.eval() before every evaluation. Not once at the start, every time, because they alternate.

eval() and no_grad() are independent and you want both: eval() changes what layers do, no_grad() changes whether a graph is built. Neither implies the other.

§15 Saving, loading, resuming

A model is its weights, and the weights are a dictionary.

torch.save(model.state_dict(), "model.pt")

model = MLP(20, 64, 2)                    # build the same architecture first
model.load_state_dict(torch.load("model.pt"))
model.eval()

state_dict() returns an ordinary dictionary mapping names to tensors: 'fc1.weight', 'fc1.bias' and so on, exactly the names named_parameters() produced in §8, plus any buffers. It is inspectable, and inspecting it is often the fastest way to understand a checkpoint someone handed you.

Pitfall: save the state dict, not the model

torch.save(model, "model.pt") also works and you should not do it. It pickles the Python object, which means the file contains a reference to your class definition and will not load if you rename the file, move the class, or change the library version.

The state dict contains only tensors and strings. It loads anywhere, and the cost is that you must construct the architecture before loading into it, which is a feature, because it forces the architecture to be written down somewhere other than a pickle.

Resuming is more than the weights

To stop a run and continue it exactly, the weights are not enough. The optimiser has state (momentum and the squared-gradient average of Part III §16), and discarding it means restarting with an empty velocity, which shows up as a visible bump in the loss curve.

torch.save({
    "epoch": epoch,
    "model": model.state_dict(),
    "opt":   opt.state_dict(),        # momentum and second-moment estimates
    "sched": sched.state_dict(),      # where the schedule had got to
}, "checkpoint.pt")

That the optimiser has a state_dict at all is a direct consequence of Part III §15: momentum is state carried between steps, which is why the optimiser had to be an object rather than a function. The checkpoint format is that design decision surfacing.

Try it

You train a model, save it, load it in a fresh script, and evaluate. The accuracy is several points lower than what training reported, and differs slightly each time you run the evaluation. Name the bug.

Answer. model.eval() was not called after loading. A freshly constructed module is in training mode by default, so dropout is active during your evaluation, deleting a random half of the units on every forward pass.

Both symptoms follow directly. Lower accuracy, because you are measuring a crippled model. Different each time, because the mask is redrawn on every pass: this is Figure 4's left-hand distribution, sampled once per evaluation.

The reason it is worth being able to name from the symptoms alone: nothing in the error output points at it, and the natural first suspicion (that the checkpoint did not load correctly) is wrong. Checking the loaded weights would show them to be perfectly correct.
