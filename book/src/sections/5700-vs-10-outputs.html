Part AWhen the output is not a label

Classification hands back one number per image and is scored by whether it is right. Every task in this part hands back a variable-length structured object, and scoring one requires deciding what counts as a match, a decision that turns out to move the answer more than most architectural choices do.

§1 The output is not a label

Three things that change at once

The output has variable length. An image contains an unknown number of objects, so the network cannot have a fixed output shape and the loss cannot be a per-slot comparison without first deciding which prediction corresponds to which object.

The output is unordered. Two predictions listing the same objects in a different order are the same answer, which is Part XXVI's permutation problem arriving in a new place.

Correctness is graded. A box that is nearly right is nearly useful, and any metric has to decide where "nearly" stops. Classification never had to.

§2 Three output spaces

And what each commits you to

Sparse and structured: detection, keypoints, tracks. A small set of objects, each with attributes. Matching is required before a loss can be computed.

Dense: segmentation, depth, flow, occupancy. One prediction per pixel, so the output shape is fixed and matching is trivial. The difficulty moves to resolution and to boundaries.

Geometric: pose, 3-D position, camera parameters. Constrained by the projection equations rather than only by the data, which means some errors are impossible to fix by training and some are impossible to make.

Most real systems produce all three and the interesting failures are at the joins.

Keypoints and pose, briefly

A keypoint model predicts a fixed, named set of points per instance (joints for a human body, corners for a vehicle), each with a location and usually a visibility flag for the ones occlusion has hidden. Regressing the coordinates directly performs badly for the same reason a squared error on box coordinates does (§14): the loss has no spatial structure to exploit. The fix that works is a heatmap per keypoint: a per-pixel probability of "the joint is here", trained with a per-pixel loss in the same spirit as §17's and read off afterwards by an argmax or a soft-argmax. The keypoint problem is a detection problem wearing a dense-prediction solution.

Multiple instances bring back §1's matching problem in a new shape: a top-down pipeline detects each instance first and predicts keypoints inside its box, inheriting detection's failure modes; a bottom-up pipeline predicts every keypoint in the image at once and then solves an association problem to group them into people, inheriting §34's. Neither side is free of the other movement's difficulty, which is why pose estimation is usually built on top of a detector or a tracker rather than replacing one.

The metric, PCK (percentage of correct keypoints), matches §4's move exactly: a predicted point counts as correct within a threshold measured as a fraction of a reference length (head or torso size) rather than a fixed pixel count, because a fixed threshold would score a close-up face and a distant pedestrian on different effective scales. This part does not carry keypoints further than this: the detection and dense-prediction machinery of movements B and C is what a pose head is built from, and nothing about it is geometry-limited the way movement D's tasks are.

§3 Boxes, and what they cannot say

Pitfall: the representation is a choice with consequences

An axis-aligned rectangle is cheap, easy to annotate and easy to score, and it cannot represent a diagonal object without including mostly background, cannot represent an occluded object's extent, cannot say which pixels belong to it, and has no orientation.

For a car directly ahead it is nearly exact. For a car at 45° it is a poor description of the same object, and a metric built on box overlap will score the second worse for reasons that have nothing to do with whether the car was found. Rotated boxes, masks and 3-D cuboids each fix part of this and each cost annotation.

§4 The metric is a threshold

Intersection over union, and the decision it forces

$$\mathrm{IoU}(A, B) \;=\; \frac{|A \cap B|}{|A \cup B|}$$

Scale-invariant, bounded, and zero for any pair that does not overlap, which is the property that makes it useless as a loss and fine as a metric.

Turning it into a score requires a threshold: above it a prediction is a true positive, below it a false positive and the object counts as missed. Average precision then ranks predictions by confidence and integrates precision over recall. Every number reported in this field is AP at some threshold, and the threshold is a modelling decision that is usually inherited rather than chosen.

§6 What AP does not measure

Five things, each of which has cost somebody a deployment

Calibration. AP is a ranking metric, so monotonically rescaling every confidence changes nothing. A detector with perfect AP can have confidences that mean nothing, and Part XIV §5's reliability check is what catches it.

Which objects were missed. Averaging over instances hides that the misses are systematically the small, the distant and the occluded, the ones that matter.

Temporal consistency. A detector that flickers between frames and one that is stable score identically on a per-frame metric, and only one is usable downstream.

The cost asymmetry. A missed pedestrian and a spurious traffic cone count the same. Part XXIV §33's threshold argument is what converts a ranking into a decision.

Whether the box was the right shape of answer at all, which is §3.

§7 Class imbalance is structural here

Not a property of the dataset

In classification, imbalance is something a dataset happens to have. In detection it is guaranteed by the geometry: an image has millions of positions and a handful of objects, so whatever the model considers, almost all of it is background.

That single fact drives the design of the loss, the sampling strategy and the training schedule, and §13 measures how extreme it is. It also gets worse with resolution, which is the opposite of what one would want.
