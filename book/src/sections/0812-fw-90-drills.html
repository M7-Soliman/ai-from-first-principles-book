PracticeDrills

Thirty-five problems. Most are diagnostic: a symptom, and the question is what causes it. That is deliberate: the skill this part is trying to build is reading a failure and knowing which derivation it violates, which is a different skill from writing code that works the first time.

Tier 0 Estimate first

EstimateE1 · How big a validation set

You want your validation accuracy to have a standard error of one percentage point. Write down the number of examples you need, before deriving it.

Answer. 2,500. The standard error is √(p(1−p)/n), worst at p = 0.5, so n = 0.25/0.0001. Most validation sets are smaller than this, which means most reported differences of a point or two are inside the noise of the set that produced them. Score yourself: within a factor of two is a pass, and an order of magnitude out is worth understanding before you go on.

Tier 1 Warm-up

WarmW1 · The five attributes

Name the five attributes of a tensor that account for most runtime errors.

Answer. shape, dtype, device, requires_grad, grad. Shapes must chain, dtypes must match, devices must match, tracking must be on, and the gradient is where the answer lands.
WarmW2 · Default dtype

What are the dtypes of torch.tensor([1.0]), torch.tensor([1]), and torch.from_numpy(np.array([1.0]))?

Answer. float32, int64, float64. Three defaults, three answers, and the third is the one that collides with a model's float32 weights.
WarmW3 · Leaf or not

In x = torch.tensor(2.0, requires_grad=True); y = x * 3, which has is_leaf == True, and which will have a .grad after y.backward()?

Answer. x is the leaf and gets the gradient. y is computed, so y.grad is None. Autograd computes intermediate gradients and discards them; you never update an activation.
WarmW4 · Parameter count

How many learnable numbers in nn.Sequential(nn.Linear(10, 20), nn.ReLU(), nn.Linear(20, 5))?

Answer. $(10{\times}20 + 20) + (20{\times}5 + 5) = 220 + 105 = \mathbf{325}$. nn.ReLU has none; it is a Module with no parameters, which is ordinary.
WarmW5 · Which loss

Your model's last layer is nn.Linear(64, 10) and you are classifying into 10 classes. Do you apply a softmax before the loss?

Answer. No. F.cross_entropy takes logits and performs the log-softmax internally, fused for the stability reason in Part II §25. Applying softmax yourself runs it twice and inflates the loss without raising anything.
WarmW6 · The missing line

A loop runs forward, loss, backward, step, and the loss diverges after about fifty steps. What is missing?

Answer. opt.zero_grad(). Gradients accumulate, so by step 50 you are stepping on the sum of fifty batches, an effective learning rate fifty times too large.
WarmW7 · Item

Why is total += loss.item() preferable to total += loss?

Answer. loss carries its whole graph, so accumulating the tensor keeps every batch's activations alive and the run eventually runs out of memory. .item() extracts a plain float and lets the graph be freed.
WarmW8 · Two modes

Which layers behave differently in train() and eval()?

Answer. Dropout (active vs disabled) and batch normalisation (batch statistics vs stored running averages). Everything else is unaffected.
WarmW9 · Save what

Why torch.save(model.state_dict(), ...) rather than torch.save(model, ...)?

Answer. The state dict holds only tensors and names, so it loads anywhere. Saving the model pickles a reference to your class definition, and breaks if the class moves, is renamed, or the library version changes.
WarmW10 · The asymmetry

model.to(device) is called once; xb.to(device) is called every iteration. Why?

Answer. Parameters persist, so moving them once is enough. Each batch is a new tensor from the loader, so it must be moved every time. Note also that the model version acts in place while the tensor version returns a new tensor; you must assign the result.

Tier 2 Core

CoreC1 · Read the graph

For loss = (torch.sigmoid(w*x + b) - y)**2 with w and b tracked, how many AccumulateGrad nodes does the graph contain, and why that number?

Answer. Two: one per leaf, so one per parameter. x and y are data and are not tracked, so they contribute no accumulation node. Figure 1 is this graph, read out of PyTorch.
CoreC2 · Why it must save

Why does a forward pass have to store activations at all? Answer in terms of one specific operation.

Answer. Because a local derivative needs a value from the forward pass. For $y=\sigma(z)$, the backward needs $\sigma(z)(1-\sigma(z))$ and therefore the value $\sigma(z)$. For $\mathbf{h}=W\mathbf{x}$, the gradient with respect to $W$ needs $\mathbf{x}$. Every operation needs some input or output of its own forward.
CoreC3 · Memory scaling

A run runs out of memory. Halving the batch is the standard first move. When does it work, and how would you tell in one experiment?

Answer. It works only to the extent you are activation-bound. The graph also saves the weight matrices, which do not scale with the batch at all, and Figure 2 shows that at width 512 a 128-fold batch increase moves total memory by only 1.6×. The experiment: halve the batch once and see whether memory follows. If it does, keep going. If it barely moves, you are parameter-bound and the levers are a smaller model, gradient checkpointing, or lower precision.
CoreC4 · Backward twice

Why does calling backward() twice raise, and when is retain_graph=True the right fix rather than a mask?

Answer. The first call frees the saved intermediates. It is the right fix when you genuinely need two passes over one graph, say two losses on shared activations. It is a mask when the real cause is a tensor from a previous iteration still attached, in which case retaining leaks memory instead of failing.
CoreC5 · In-place, sometimes

Why does b = torch.sigmoid(a); b.mul_(2); b.sum().backward() raise, while b = a * 3; b.mul_(2); b.sum().backward() does not?

Answer. Sigmoid's backward needs its own output, which the in-place multiply overwrote; the version counter catches it. Multiplication's backward needs the other operand, not its output, so overwriting the result is harmless. In-place is dangerous exactly when the overwritten value is one a backward depends on.
CoreC6 · Three ways to stop

Distinguish no_grad(), detach() and requires_grad_(False) by what each is scoped to.

Answer. no_grad() scopes to a region of code; detach() to a single tensor; requires_grad_(False) to a parameter for the rest of its life. Evaluation uses the first, logging the second, freezing a backbone the third.
CoreC7 · The list bug

self.layers = [nn.Linear(64,64) for _ in range(8)]. What happens, and what single command reveals it?

Answer. A list is not a Module, so nothing is registered. Those eight layers never appear in parameters(), are never given to the optimiser, and stay at their random initialisation forever. Reveal it with sum(p.numel() for p in model.parameters()). Fix with nn.ModuleList.
CoreC8 · Why super

What breaks if you omit super().__init__() in a Module subclass?

Answer. The internal registries never exist, so assigning a submodule or parameter either raises or registers nothing. parameters(), state_dict(), .to() and .train() all depend on them: assignment to a Module attribute is intercepted, not ordinary.
CoreC9 · Parameter or buffer

A batch-norm running mean is saved with the model and moved to the GPU with it, and must not be updated by the optimiser. Which is it, and why does the distinction exist?

Answer. A buffer. "Part of the model" and "updated by gradient descent" are different questions: the running mean is estimated from data, not learned, so the Module system answers them separately.
CoreC10 · Decode a shape error

mat1 and mat2 shapes cannot be multiplied (8x7 and 10x5), raised inside an nn.Linear. What did you build, and what did you feed it?

Answer. The layer is nn.Linear(10, 5): the message reports the weight already transposed for the multiply, so 10x5 is in×out, not the stored shape $(5,10)$. You fed it a batch of 8 examples of width 7. The layer wants width 10.
CoreC11 · Two dtype errors

You load features and labels the same way from NumPy. Name the two errors, in order, and the two opposite fixes.

Answer. Features: mat1 and mat2 must have the same dtype, but got Double and Float, float64 data, float32 weights, fixed with .float(). Labels: expected scalar type Long but found Double: cross-entropy wants class indices, fixed with .long(). Features want floats, labels want integers.
CoreC12 · Non-scalar backward

grad can be implicitly created only for scalar outputs. What did you do?

Answer. Called backward() on a tensor with more than one element, most often a loss with reduction="none", which returns one value per example. A gradient is defined with respect to a scalar (Part 0 §23). Add the missing .mean().
CoreC13 · The silent evaluation bug

A loaded checkpoint evaluates several points below its training score, and differs each run. Diagnose from the symptoms alone.

Answer. Missing model.eval(): a fresh module is in training mode, so dropout is active. Lower, because you are measuring a crippled model; different each time, because the mask is redrawn. Figure 4 is this distribution.
CoreC14 · Shuffle

Your loss curve oscillates with a period exactly equal to one epoch. What is the most likely cause?

Answer. shuffle=False on data with meaningful order: sorted by class, date or source. Each batch is then drawn from a different distribution, the gradient estimate is no longer unbiased (Part II §17), and the model chases whichever region it is passing through.
CoreC15 · Resuming

You save only model.state_dict() and resume from it. The loss shows a visible bump at the resume point. Why?

Answer. The optimiser state was discarded. Momentum and the squared-gradient average of Part III §16 restart from zero, so the first steps after resuming are effectively unmomented and mis-scaled. Save opt.state_dict() too.
CoreC16 · Accumulation, deliberately

You want an effective batch of 128 but only 32 fits. Write the loop, and say why the loss must be divided.

Answer. Call backward() on each of four batches and only then step() and zero_grad(). Divide the loss by 4 because each is already a mean over its batch: summing four means without scaling gives four times the intended gradient.
CoreC17 · Order matters

Where may zero_grad() go in the loop, and where may it not?

Answer. Top of the loop, or immediately after step(), both correct. Never between backward() and step(), which erases the gradients just computed and makes the optimiser a no-op.
CoreC18 · Which zero

After backward(), a parameter's p.grad is None. A different one is exactly 0.0. Do these mean the same thing?

Answer. No. None means the parameter was never in the graph: unregistered, detached, or frozen. Exactly zero means it was in the graph and the gradient genuinely came out zero, which points at a dead ReLU (Part VII §19) or a broken path. Different causes, different fixes.

Tier 3 Stretch

StretchS1 · Measure the graph

Write code that walks loss.grad_fn.next_functions recursively and prints every node type. Run it on a two-layer MLP. How many nodes, and can you name each?

Answer. You will find AddmmBackward (the fused $XW^\top+b$ of a linear layer), ReluBackward, NllLossBackward and LogSoftmaxBackward from the fused cross-entropy, and one AccumulateGrad per parameter tensor: four for two linear layers. This is how Figure 1 was produced.
StretchS2 · Reproduce Figure 2

Measure retained activation memory by traversing the graph and summing every _saved_ tensor. Confirm it is linear in batch size and in depth.

Answer. Both linear, as the figure shows. The instructive part is what is not counted: the parameters themselves, which do not scale with batch. On a wide, deep model at a large batch, activations dominate parameter memory by an order of magnitude or more.
StretchS3 · Reproduce Figure 4

Forward one fixed input through a model with dropout 2,000 times in each mode. Report both standard deviations.

Answer. In train() the spread is substantial, about 0.26 for the model in the figure. In eval() it is exactly zero: dropout is disabled, so the function is deterministic. That contrast is the whole argument for the discipline in §14.
StretchS4 · Batch and throughput

Time forward+backward across batch sizes 1 to 256 on one thread. Plot examples per second. Where does the curve flatten, and what does that tell you?

Answer. Figure 3 measured a factor of about 72 from batch 1 to 256. It flattens once the matrices are large enough to keep the arithmetic units busy; past that, extra batch buys memory pressure rather than speed. Combined with Part III §14's $1/\sqrt{b}$ noise argument, that flattening point is a reasonable place to look for a batch size.
StretchS5 · Gradient check a Module

Write a custom torch.autograd.Function with a deliberately wrong backward (off by a factor of two) and confirm gradcheck catches it. Then fix it.

Answer. gradcheck compares against numerical differentiation and fails loudly. Note it requires float64 inputs, for Part III §3's reason: the central difference loses digits to cancellation and float32 has none to spare. That constraint is a numerical fact appearing as an argument requirement.
StretchS6 · Find the leak

Write an evaluation loop that leaks memory, measure the growth, then fix it two different ways and confirm both work.

Answer. Appending model(xb) without no_grad retains a graph per batch, so memory grows linearly with batches processed. Fix by wrapping in torch.no_grad() (better: no graph is built at all) or by appending .detach() (works, but pays to build the graph first). Measuring the growth is the point: it makes the graph's cost concrete.
