Part BMaking it fast

Two transformations account for most of the speed in numerical code, and neither changes the arithmetic: do more per pass over the data, and arrange for the data to be somewhere close. Everything a compiler does automatically is one of those.

§9 Fusion

Fewer trips

A chain of elementwise operations, each written as its own kernel, reads the whole array from memory and writes it back once per operation. Fusing them into a single pass reads once, does all the arithmetic in registers, and writes once.

The arithmetic is identical. The traffic falls by roughly the chain length, and since the chain was memory-bound the time falls with it. This is the single most valuable transformation in numerical code and it is why a compiler exists at all.

§11 Blocking

Working on a piece that fits

A matrix multiplication written in the obvious order streams through both inputs repeatedly, and once they exceed cache each pass fetches from main memory again. Splitting the computation into blocks small enough that a block of each input fits in cache means each block is fetched once and reused many times.

The arithmetic is identical again. The traffic falls by a factor of the block size, and the right block size is the one whose working set matches a level of the hierarchy, so it can be computed rather than searched.

§13 What a compiler does

Four transformations, and the reason a graph is captured first

Fusion, §9. Layout selection: choosing how tensors are arranged in memory so the access pattern is contiguous. Algebraic simplification: cancelling operations that neighbour each other. Kernel selection: picking an implementation for the shapes at hand.

All four need the whole computation visible at once, which is why frameworks capture a graph before optimising. It is also why anything that breaks capture (a data-dependent branch, a shape that changes every call) silently returns you to unfused execution, and the symptom is a model that is mysteriously slower after a small change.

§14 Writing a kernel

When it is worth doing by hand, and the shape of the work

Write a kernel when the operation is memory-bound, appears in a chain, and the compiler will not fuse it: a custom attention variant, a fused optimiser step, a quantisation routine. Not for matrix multiplication, where the vendor's implementation is the product of person-years.

The shape of the work is always the same: decide which piece of the output each unit of parallelism produces, load the inputs it needs into fast memory once, compute, write once. Modern tooling lets that be expressed at the block level rather than the thread level, which removes most of the difficulty and none of the thinking.

Triton is that tooling in its most direct form: a kernel is a Python function decorated @triton.jit, written once per block rather than once per thread: you name the tile a program instance owns, tl.load it, compute, tl.store it back, and the compiler handles the thread-level scheduling and register allocation the hand-written version above does implicitly. It is the same three-step shape as §9's fusion and drill S1's numpy kernel, at the level a GPU actually executes it. This book's snippets are run and checked before they ship, per this book's own rule, and that rule is exactly why a Triton listing is not printed here: the execution environment behind these pages has no GPU to run one against, so the honest choice is to describe the model rather than paste an unverified kernel. The numpy fusion in Figure 2 and drill S1 is the same idea, checked on hardware this book does have.

§15 Reading a profile

In order, and stop when you have the answer

Where does the time go? Usually a handful of kernels. Optimise anything else and the total will not move (Amdahl, arriving as a scheduling decision).

Is that kernel memory-bound or compute-bound? Compute its arithmetic intensity and place it on Figure 1's plot.

How close is it to the relevant ceiling? A memory-bound kernel at 80% of bandwidth is finished. One at 15% has something wrong with its access pattern.

Only then look at occupancy, and only to explain what you already measured.

Three things

The two transformations that matter change no arithmetic. Fusion reduces trips; blocking reduces distance.
