Part BThe graph

One idea explains nearly every autograd behaviour, every autograd error, and most of the memory a training run consumes: as your code executes, the library records what it did. This part is about that recording: what goes into it, when it is thrown away, and how to stop it.

§4 requires_grad, and what it spreads to

In 60 seconds

Marking a tensor requires_grad=True says "I want derivatives with respect to this". The flag is contagious: any result computed from a tracked tensor is itself tracked, and remembers the operation that produced it. Following those links backwards from the loss is the chain rule of Part 0 §17, organised.

By default a tensor is inert. It holds numbers and nothing else:

x = torch.tensor(2.0)
y = x * 3
y.grad_fn                  # None -- nothing was recorded

Set the flag and the same arithmetic starts leaving a trail:

x = torch.tensor(2.0, requires_grad=True)
y = x * 3
y.requires_grad            # True        -- it spread
y.grad_fn                  # <MulBackward0>  -- and it remembers how

The spreading is the important half. You never mark intermediate values; you mark the parameters, and everything downstream inherits tracking because it depends on them. That is why nn.Linear sets the flag on its weight and bias and on nothing else: those are the only things being learned, and the rest follows.

Intuition: the flag answers "is this on the path to a parameter?"

A tensor has requires_grad=True exactly when it was computed, however indirectly, from something being learned. Data does not require grad. Labels do not. Activations do, because they descend from weights.

So the flag is not a property you assign to things; it is a fact about the dependency structure, computed for you. The only ones you set by hand are the roots.

§5 The graph, seen

Go and read

Paszke et al. (2019), PyTorch: an imperative style, high-performance deep learning library. The design paper for the library you are learning, and worth reading for the argument rather than the API. It is an explicit defence of building the graph as the code runs, against the then-dominant approach of declaring it first, and it is candid about what that choice gives up. Read it against Abadi et al. (2016) on TensorFlow, which made the opposite call. Either alone reads as inevitable; the pair makes the design space visible.

Take the model from Part 0 §24 (one weight, one bias, a sigmoid and a squared error) and ask PyTorch what it recorded.

w = torch.tensor(0.5, requires_grad=True)
b = torch.tensor(0.0, requires_grad=True)
x = torch.tensor(2.0)

z     = w * x + b
y_hat = torch.sigmoid(z)
loss  = (y_hat - torch.tensor(1.0)) ** 2

Read the chain against Part 0 §24's three factors. Pow is $\partial L/\partial \hat{y} = 2(\hat{y}-y)$. Sigmoid is $\sigma(z)(1-\sigma(z))$. Mul is $\partial z/\partial w = x$. The multiplication of those factors that you did by hand is the reverse traversal of this graph, and the two AccumulateGrad nodes are where the answers were written down.

Definition: leaf and non-leaf

A leaf is a tracked tensor you created directly, rather than one computed from others. Parameters are leaves; activations are not.

t.is_leaf reports which. It matters because only leaves get a .grad.

x = torch.tensor(2.0, requires_grad=True)
y = x * 3
y.backward()

x.is_leaf, y.is_leaf       # True, False
x.grad                     # tensor(3.)
y.grad                     # None  -- and a warning

That None surprises people, and the reason is economy. In a real network there are millions of intermediate tensors and a few thousand parameters. Storing a gradient for every intermediate would multiply memory for no benefit, because you are never going to update an activation; you update weights. So autograd computes intermediate gradients, passes them backwards, and discards them.

If you genuinely want one, ask before the backward pass:

y = x * 3
y.retain_grad()            # keep this one
y.backward()
y.grad                     # tensor(1.)

§6 What backward() does, and what it destroys

Calling backward() on a scalar does three things: it seeds the output gradient with 1, walks the graph in reverse topological order accumulating into every .grad, and then frees the intermediate values it saved.

That third step is not a detail. It is why this fails:

y = x * 3
y.backward()
y.backward()               # RuntimeError: Trying to backward through the graph
                           # a second time ...

The error is not saying you may not differentiate twice. It is saying the values needed to do so are gone. Passing retain_graph=True to the first call keeps them, at the cost of the memory Figure 2 measures.

Why anything needs saving at all

Part VII §17 makes the general argument; here it is concretely. To send a gradient back through $y = \sigma(z)$ you need $\sigma'(z) = \sigma(z)(1-\sigma(z))$, which requires the value $\sigma(z)$ computed on the way forward. Through a matrix multiply $\mathbf{h} = W\mathbf{x}$ you need $\mathbf{x}$ to compute the gradient with respect to $W$. Every operation's backward needs some input or output of its forward.

So a forward pass through a deep network leaves behind one saved tensor per operation, per example in the batch, and they must all survive until the backward pass reaches them.

That left-hand shape is worth stopping on, because it contradicts the tidy rule people usually carry, that training memory is batch × depth × width.

The graph is holding two different kinds of thing, and only one of them scales with the batch.

  • Activations: one per operation per example. These are linear in batch size, and they are what everyone means by "activation memory".
  • Parameters: because equation 3 of Part VII §14 computes $\partial L/\partial W$ from the layer's input, and equation 2 needs $W$ itself to push the gradient backward. So the weight matrices are saved too, and a weight matrix does not care how many examples you sent through it.

Which term dominates is a race between $\text{batch} \times \text{width}$ and $\text{width}^2$. At width 512 a single layer's weights are 262,144 numbers while one example's activations are 512, so the parameters win by a factor of 512, and the batch has to grow enormously before it matters. At width 64 with a batch of 256 the balance has tipped the other way.

Why the correction matters in practice

"Halve the batch" is the standard first move against an out-of-memory error, and this figure says when it will work and when it will not.

On a wide model at a small batch (the left of those curves), halving the batch buys almost nothing, because you are not paying for the batch. People do it anyway, watch memory barely move, and conclude something exotic is wrong. Nothing is: the memory was in the weights and the saved copies autograd needs of them.

On the linear stretch it works exactly as advertised. So the useful diagnostic is to halve the batch once and see whether memory follows. If it does, you are activation- bound and can keep going. If it does not, the lever you need is a smaller model, gradient checkpointing, or lower precision (Part III §1).

Why this is the memory model to carry

Model parameters are usually the smaller half of what a training run holds. A network with ten million parameters occupies 40 MB in float32, which is trivial. Its activations, at a batch of 256 and a depth of fifty, can be many gigabytes, because they scale with batch size and the parameters do not.

Three consequences follow, and all three are standard practice:

  • Inference needs far less memory than training, because with no backward pass nothing has to be saved. That is what torch.no_grad() exploits.
  • Halving the batch halves the activation term, but only that term, which is why the figure above says to check that memory actually followed.
  • Gradient checkpointing (Part VII §17) throws activations away and recomputes them during the backward pass, trading time for memory. It is only a sensible trade because of the scaling this figure shows.

§7 Stopping the gradient

Three tools, doing three different things, routinely confused.

ToolEffectUse when
torch.no_grad()records nothing inside the blockevaluating, or updating weights by hand
t.detach()returns a copy with the parent link cutyou want the value but not its history
p.requires_grad_(False)stops tracking a parameter permanentlyfreezing part of a model

The distinction that matters: no_grad is about a region of code, detach is about a single tensor, and requires_grad_ is about a parameter for the rest of its life.

torch.inference_mode() is a stricter sibling of no_grad(), now the recommended default for pure evaluation: it also disables the version-counter bookkeeping that the in-place checks below rely on, since nothing built under it will ever be backpropagated through, which buys a further speedup at the cost of a tensor made under it being unusable if you later try to feed it into a graph that does need gradients.

# evaluating: no graph needed, so build none
with torch.no_grad():
    preds = model(X_val)

# freezing a pretrained backbone, training only the head
for p in model.backbone.parameters():
    p.requires_grad_(False)

# logging a value without keeping its graph alive
history.append(loss.detach())      # or loss.item(), per section 3

In-place operations, and why they are not simply banned

Any method ending in an underscore modifies its tensor in place: x.add_(1), x.mul_(2), x.relu_(). They save memory, and they can corrupt a backward pass by overwriting a value some operation still needs.

PyTorch does not forbid them. It version-counts every tensor and raises if a saved value was modified before it was used:

a = torch.randn(3, requires_grad=True)
b = torch.sigmoid(a)
b.mul_(2)                    # overwrite sigmoid's output ...
b.sum().backward()
### RuntimeError: one of the variables needed for gradient computation
### has been modified by an inplace operation ... is at version 1;
### expected version 0 instead.

But the same pattern on a different operation is fine:

b = a * 3                   # multiplication's backward needs the OTHER operand,
b.mul_(2)                    # not its own output
b.sum().backward()          # no error

That contrast is the whole rule. In-place is dangerous exactly when the overwritten value is one a backward pass depends on, and which values those are depends on the operation. The library cannot forbid the pattern without losing a real memory saving, so it detects the failure instead, which is a considerably better bargain than your own engine in Part VII §21 offers, since that one would silently return a wrong gradient.

Try it

You write an evaluation loop that runs correctly but uses far more memory than training did, and eventually runs out. The loop is:

for xb, yb in val_dl: preds.append(model(xb))

What is wrong, and what are the two independent fixes?

Answer. Every model(xb) is computed with grad tracking on, so each appended prediction drags its whole graph (all the saved activations of §6) into the list. Nothing is ever freed, so memory grows with the number of batches. Training did not have this problem because backward() freed each graph immediately.

Fix one: wrap the loop in with torch.no_grad(): so no graph is built at all. This is the right answer, and it is also faster.

Fix two: append model(xb).detach(), which cuts the link so the graph can be collected. This works but still pays to build the graph first. The two compose, and in practice you use the first; the reason to know both is that the second is what you need when only part of a computation should be excluded.
